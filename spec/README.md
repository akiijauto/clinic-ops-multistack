# 契約 — これが唯一の正

**5つの実装は、この `spec/` に対して作られる。** レーン同士は互いを見ない。
実装の言語もフレームワークも自由だが、**外から見た振る舞いはここで決まる**。

## 読む順番

1. **`README.md`（この文書）** — 範囲と、何を簡略化したか
2. `model.md` — データの形
3. `screens.md` — 26画面と、それぞれ何ができれば良いか
4. `acceptance.md` — **数値の受け入れ条件（検算）**
5. `openapi.yaml` — HTTPの契約

## 範囲について（指揮役の判断・2026-09-05）

題材にしている実システムを実測したところ、**28のモデルと42のルート**があった。
マスタ管理まで含めて5つの実装へ丸ごと複製するのは、**この企画の目的に対して過剰**である。

目的は「同じ問題を別の道具で解くと何が変わるか」を測ることで、
**マスタ管理の作り込みを5回繰り返すことではない。**

そこで次のように決めた。

| | 決定 |
| --- | --- |
| **画面** | **26枚すべて作る。** 幅がこの企画の中身なので削らない |
| **データモデル** | **絞る。** 28 → 14 程度（`model.md` に理由つきで記載） |
| **マスタ管理の画面** | **一覧と参照は作る。編集は作らない。** 初期データを読み込む形にする（線引きは下記） |

### 何を落としたか（隠さずに書く）

落としたものは `model.md` に**1つずつ理由を添えて**書く。
公開したときに「作れなかった」と読まれないよう、**意図して外したことが分かる形**にする。

**やってはいけないこと**: 落としたものを黙って落とすこと。
画面に「できます」と書いてあって出来ていない状態を作らないこと。

## 振る舞いの原則（迷ったらここへ戻る）

`DECISIONS.md` 第4節と同じもの。契約に書いていないことはこれで決める。

| 論点 | 決め |
| --- | --- |
| 数値の丸め | `acceptance.md` の規則に従う。書いていなければ**丸めない** |
| 日付・時刻 | **JST**。集計の月境界もJST |
| 文字数 | **文字数で数える**。バイト数で数えない |
| 未入力の金額 | **0として集計しない。** 未算入の件数を明示する |
| エラーの文言 | `openapi.yaml` のものを**一字一句**使う |
| 画面の見た目 | **各スタックの流儀でよい。** 揃えるのは振る舞いだけ |

### 「未入力を0として集計しない」について

これは題材の実システムで**実際に出た不具合**である。
単価が設定されていない明細行を0円として合計に入れており、
**合計は出るがエラーも出ず、ただ実際より小さい**という状態になっていた。

対処として「合計を表示しない」ではなく、**合計は出し、未算入の行数を併記する**形にした。
合計が出ないと、使う側は次に何をすればいいのか分からないからである。

> 間違った数字を黙って出すのが最悪。**次に何をすればいいか分からない画面は、その次に悪い。**

5実装ともこの形にすること。

### 「保存できる」と「表示だけ」の線引き

「マスタ編集は作らない」と「設定の値を保存する」が重なる。**画面ごとに決めておく。**
決めないと5レーンが別々の線を引く。

| 画面 | 扱い |
| --- | --- |
| **設定**（病院の情報・消費税・休診日） | **保存できる。** `Clinic` は変わるものなので |
| **機能設定** | **表示だけ。** `ClinicFeature` を落としたので、切り替える対象が無い |
| **取込** | **表示だけ。** 何を取り込めるかの説明に留める |
| **マスタ**（料金・検査項目・種別） | **表示だけ。** 固定データ（`data/`）を読んで見せる |
| **スタッフ** | **保存できる。** `Staff` は変わるもの |

**表示だけの画面に、押せる保存ボタンや入力欄を置かないこと。**
「できます」と見せて出来ていない状態を作らない。
**この企画では作っていない**と画面上で分かるようにする。

## HTMLの目印（2種類ある。役割が違う）

画面の見た目は各スタックの流儀でよいが、**共通テストが機械で読めるように目印を置く**。
2種類あり、**答える問いが違う**。

| 目印 | 答える問い | 定義している文書 |
| --- | --- | --- |
| **`data-testid`** | **その要素があるか** | `openapi.yaml`（各画面の `x-data-testids`） |
| **`data-check`** | **その値が正しいか** | `acceptance.md`（キーの一覧表） |

例:

```html
<div data-testid="screen-accounting">
  <span data-check="billing.net_amount">12,000</span>
  <span data-check="billing.excluded_count">2</span>
</div>
```

どちらも属性なので**見た目には影響しない**。

**なぜ2種類なのか**: 「画面が出ているか」と「出ている数字が正しいか」は別の問いだから。
前者だけ見ていると、**画面は出るが数字が間違っている**状態を通してしまう。
題材の実システムで実際に起きた不具合（全患者のカルテに同じ体温が印字される）が
まさにそれで、APIの値は正しかった。

## CSVの文字コード

`/dm.csv` が返すCSVは **UTF-8（BOMつき）**、改行は **CRLF** とする。

BOMを付けるのは、**日本語のCSVをExcelで開いたときに文字化けさせないため**。
BOMが無いとExcelは既定の文字コードで開こうとして崩れる。
「書き出せたが開けない」は、書き出せていないのと同じである。

決めておかないと5実装で別々になり、**同じデータなのに開ける実装と開けない実装**ができる。

## 保存について

**書き込みは受け付ける。** 題材の評価版は読み取り専用だが、それは配備先の都合であって
仕様ではない。この企画では**保存まで動く**ものを作る。

保存先は各レーンが選んでよい（`DECISIONS.md`）。**追加インストールが要らないもの**に限る。
SQLite を推奨する。

## 完了の判定

レーンが「終わった」と言えるのは次のすべてを満たしたときだけ。

1. **共通テスト（`tests/`）が緑**。自分で書いたテストが緑でも完了ではない
2. `acceptance.md` の**検算がすべて一致**する
3. **テストの期待値を実装に合わせて書き換えていない**
4. **部分実行の緑を緑と呼ばない。** 最後の変更のあとに全体を流す
5. **死んだリンクが無い**（画面が26枚あるので目視では無理。機械で確かめる）

## この契約は凍結されている

変更が要るときは**全レーンを止めて指揮役が判断する**。
レーンが勝手に変えない。`spec/` と `tests/` を書き換えないこと。

契約に欠陥を見つけたら `coordination/qa/lane-*.md` に書いて、**実装が止まるなら指揮役へ直接**言うこと。
