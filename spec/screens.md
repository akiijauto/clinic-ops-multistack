# 画面 — 26画面の契約

**ここに書いた4項目（何をする画面か／表示するもの／できること／満たすべきこと）が、
5レーンが揃えるべき振る舞いのすべて。** 見た目（色・部品の形・レイアウト）は各スタックの
流儀でよい。「満たすべきこと」は機械で確かめられる言い方にしてある——
`tests/` はここに書いた条件をそのままアサーションにする。

対象は `docs/実装分担-2026-09-05.md`（2026-09-05 オーナー判断）で
**これから出来上がると決まっている姿**。現在の題材が読み取り専用・一部未実装なのは
配備先の都合であり、この契約の姿ではない（`spec/README.md`「保存について」）。

## 共通の約束

### ボタンの3状態

画面上のボタン・リンクは、常にこの3つのどれかである。**4つ目（「まだ実装していません」）は無い**
——26画面はすべて完成させる（`spec/README.md`）。

| 状態 | 見え方 | 押したときの遷移先 |
| --- | --- | --- |
| **A. 動く** | 通常の見た目で押せる | 実際の処理が起きる |
| **B. この企画では作っていない** | 押せる見た目のまま無効（グレー）。**消さない** | 理由が読める（下記②③） |
| **C. あえて動かさないと決めたもの** | 同上 | 理由が読める（下記②） |

- **B**＝`model.md`「落としたもの」に対応する機能（分院・レセプト・監査ログ・
  マスタの編集画面 等）。この企画のスコープそのものに無い
- **C**＝スコープには入っているが、業務上の理由で意図して押せなくしたもの
  （例：完了行を消す操作。**消すとその日の件数が数えられなくなる**ため）
- **「B」と「C」を同じ見た目にしない。**理由の中身が違う
  （B＝「この企画では扱わない」／C＝「動くが、あえて塞いである」）ので、
  押した先の文言も分けること

### 押した先の2画面（②③）

- **②ToDo** — **個別**の理由。画面のどこかのボタンを押すと、そのボタん1つについて
  「なぜ押せないか」を返す。**C の説明はここに集約する**
- **③折りたたみ表示** — **一覧**。この企画で扱わないと決めたもの全部を1画面に並べる
  （`model.md`「落としたもの」表がそのまま元ネタ）。**B の説明はここに集約する**
  （個別のボタンを押しても③へ飛んでよい。1件だけ見せるか、その項目にスクロールするかは自由）

### 削除の扱い（全画面共通）

`Owner` `Patient` `Visit` は**物理削除しない**（`model.md`）。「削除」ボタンがある画面は、
すべて `deleted_at` に日時を入れるだけの操作であり、**行も中身も残る**。
一覧には既定で出ない。**「削除済みも表示」を選べば見える**（各画面の一覧に共通）。

### 未入力の金額（会計・売上に共通）

`BillingDetail.unit_price` が未設定の行は、**合計に0円として含めない**。
合計は出したうえで、**未算入の行数（件数）を必ず併記する**（`spec/README.md`）。
この規則は「会計」画面だけでなく、その値を使う「会計履歴」「売上集計」にも及ぶ。

### 数値・日時の扱い

**丸めない**（書いていない限り）。日付・時刻・月境界は**JST**。文字数は
**Unicodeコードポイント数**で数える（バイト数で数えない）。丸めが要る箇所は次の3つだけで、
どれも**最後に1回だけ**行う（`acceptance.md`「数値の規則」）。

| 対象 | 丸め方 | 画面 |
| --- | --- | --- |
| 伝票の税抜合計・消費税額・税込合計 | 消費税額は課税対象額×税率を**伝票につき1回だけ**円未満切り捨て。税抜・税込は表示の最後に1回だけ切り捨て | 会計・会計履歴 |
| 売上集計の構成比 | 最大剰余法で小数第1位まで（合計が必ず100.0%になる） | 売上集計 |
| 上記以外 | 丸めない | 全画面 |

**丸めた値を積み上げて再合計しない。** 明細1行ごとに丸めてから足すと、行数ぶん誤差が積み上がる。
合計は丸める前の値で計算し、表示の直前に1回だけ丸める。

### 画面の値を機械で確かめる印（`data-check`）

**26画面を目視で全部確認するのは不可能。** そこで、下表の値には**見えない目印**として
`data-check="<キー>"` を持つ要素で値を囲むこと。見た目（何のタグを使うか・CSS）は自由
（属性はレンダリングに影響しない）。値は「その要素のテキストから、前後の空白と桁区切りの
カンマを除いたもの」として読む。

| キー | 意味 | 現れる画面 |
| --- | --- | --- |
| `billing.net_amount` | 伝票の税抜合計 | 会計・会計履歴・その印刷 |
| `billing.tax_amount` | 伝票の消費税額 | 同上 |
| `billing.total_amount` | 伝票の税込合計 | 同上 |
| `billing.excluded_count` | 未算入の明細行数（0件でも要素ごと消さない） | 同上 |
| `progress_note.temperature_c` / `pulse` / `respiration` / `body_weight_kg` | 経過記録の各値（行ごと） | カルテ・その印刷 |
| `lab_test_item.value` | 検査項目の値 | 検査 |
| `lab_test_item.judgment`（値は空／`H`／`L`） | 検査項目の判定 | 検査 |
| `data-check-flag`（`normal`／`high`／`low`。`judgment` と同じ要素かその親に付く） | 判定の状態（色分けの根拠） | 検査 |
| `sales_summary.net_amount`（`data-check-axis`＝`category`\|`staff`\|`date`\|`total`、`data-check-key`＝分類名／スタッフID／日付） | 売上集計の行合計・総合計 | 売上集計 |
| `sales_summary.share_pct`（`data-check-axis="category"` の行のみ） | 分類別の構成比 | 売上集計 |
| `visit_count.today` | 対象日の診察件数 | トップ・本日の患者 |
| `care_record.performed_by` | 入院の記録行の実施者名（空にしない） | 入院 |

**この表に無い目印を勝手に増やさない。** 追加が要ると分かったら指揮役へ報告する
（`acceptance.md`「共通の確認手段」手段B）。

## 領域1｜受付・患者（8画面）

### 1. 本日の患者（受付一覧）

**何をする画面か**
1日の受付を1つの表で見る、業務の起点。行を選ぶと、その患者の各画面へ進める。

**表示するもの**
- `Reception` を**受付区分（`data/masters.json` の受付区分）ごとのタブ**で絞った一覧。
  各行は `Reception.display_no` の順（完了は下へ）
- 列：カルテNo・飼主名・品種・動物名・受付日時・オーナー目的・診療目的・状況・担当
  （`Patient` `Owner` `Reception` から引く）
- 完了件数（表示中の完了行数）
- **対象日の診察件数**（`Visit` の件数。`Reception` の完了件数とは別の数値。
  `data-check="visit_count.today"` を付ける）

**できること**
| 操作 | 起きること |
| --- | --- |
| 区分タブを押す | その区分の当日ぶんだけに絞る |
| 行を選ぶ | その行が選択状態になり、下記の患者依存の操作が有効になる |
| 「完了表示」を切り替える | 完了行を出す／隠す（既定は出す）。**行は消えない** |
| 上へ／下へ（選択行のみ有効） | 選択行の `display_no` を1つ前後と入れ替える |
| 顧客／カルテ／会計／予約（行を選んでから） | その患者の該当画面を開く |
| 分院の切り替え | **状態B**（`model.md`：病院は1件だけ扱う） |
| 完了全削除／完了削除 | **状態C**（完了行を消すと当日件数が数えられなくなるため） |

**満たすべきこと**
- 行を選ぶ前は、患者に依存する操作（顧客・カルテ・会計・予約・上下送り）がすべて無効である
- 上へ／下へを押すと、押した行と隣接する行の `display_no` が入れ替わり、**他の行の順序は変わらない**
- 一覧の並びは常に `display_no` 昇順（完了を下に送る規則は別途）で、リロードしても同じ順になる
- 完了表示を隠しても、`Reception` の行数（`deleted_at` を持たない件数）は変化しない
- 当日（JST の 0:00〜24:00）に受け付けた行だけが出る
- `data-check="visit_count.today"` の値は、その日に作成された `Visit` を後から削除
  （`deleted_at` を設定）しても**変化しない**（検算9。削除は一覧表示から隠すだけで、
  実績としての件数は減らない）

### 2. 新規登録

**何をする画面か**
飼主とその1頭目をまとめて登録する。既存の飼主に2頭目以降を足す入口も兼ねる。

**表示するもの**
- 飼主欄（`Owner`：氏名・カナ・住所・電話 等）。**既存の飼主に足すときはこの欄を出さない**
- 動物欄（`Patient`：氏名・カナ・種別・品種・性別・生年月日）
- 次に割り当てられる `karte_no`（保存前から見える）

**できること**
- 登録：`Owner`（新規登録時のみ）と`Patient`を1回の操作で作成する
- 既存の飼主IDを指定して開いたときは、`Patient` だけを追加作成する

**満たすべきこと**
- **飼主だけが存在してPatientが無い状態を作れない。**動物欄を空のまま送信したら保存は成立しない
- 保存すると新しい `karte_no` が発行され、既存のどの `karte_no` とも重複しない
- 送信直後、その `karte_no` で顧客画面を開くと、いま入れた内容がそのまま出る

---

### 3. 顧客

**何をする画面か**
飼主・動物の基本データを見る／直す。この患者に関する他画面への入口でもある。

**表示するもの**
- `Owner`（氏名・カナ・住所・電話・`owner_no`）と `Patient`（氏名・カナ・種別・品種・性別・
  生年月日・`karte_no`）
- 未収金・内金の有無（`Billing.paid_amount` 等から導く要約）

**できること**
| 操作 | 起きること |
| --- | --- |
| 保存 | `Owner` `Patient` の項目を更新する |
| 飼主削除 | `Owner.deleted_at` に日時を入れる（**物理削除しない**）。紐づく `Patient` は消えない |
| 動物削除 | `Patient.deleted_at` に日時を入れる（同上） |
| 番号変更 | `karte_no` または `owner_no` を、**未使用の値にだけ**付け替える |
| 診察券発行 | この患者の `karte_no`・氏名・飼主名を載せた印刷用の1枚を表示する |
| 文書印刷 | `data/masters.json` の定型文とこの患者の情報を合成した文書を表示する |
| 品種リスト | 動物種に応じた品種の候補を一覧で見る（入力の手掛かり。品種欄はマスタで縛らない自由入力のまま） |

**満たすべきこと**
- 飼主削除・動物削除のあと、その `Owner`／`Patient` の行はDBに残っており、`deleted_at` が入っている
- 削除した患者は「本日の患者」「検索」の既定表示から消える。「削除済みも表示」を選ぶと出る
- 番号変更は、変更先の番号が**既に使われている**場合は保存を拒否し、元の番号のままになる
- 診察券発行・文書印刷は、表示のたびに**その時点の**患者・飼主データを使う（保存はしない）

---

### 4. 検索

**何をする画面か**
飼主・動物を1手で見つける。診察の中身（病名・稟告・現症・処置）からも引ける。

**表示するもの**
- 「飼主・動物」の一覧（`Owner` `Patient` を氏名・カナ・`karte_no`・電話番号で検索）
- 「診察の中身」の一覧（`Visit` の主訴・症状・診断・処置を全文検索）。**当たった欄と前後の文字**を出す

**できること**
- 検索語を入れて実行する。2つの一覧は**独立に**表示される（片方が0件でも、もう片方は出す）
- 一覧の行から、該当する顧客画面／カルテ画面（該当 `Visit` を開いた状態）へ1手で移る

**満たすべきこと**
- 検索語が空のときは、どちらの一覧も出ない（案内文だけを出す）
- 「飼主・動物」が0件でも「診察の中身」に当たりがあれば、その旨と結果を両方出す（黙って一方だけ出さない、の逆）
- `deleted_at` が入っている `Owner` `Patient` `Visit` は既定では検索結果に出ない

### 5. 来院履歴

**何をする画面か**
その動物・飼主に関わる登録・修正・削除を、新しいものから並べて見る。**中身は書き換えない記録**。

**表示するもの**
- 日時・対象・操作（登録／修正／削除／復元）・担当（`Staff`）・変わった内容（前後の値）
- 削除した `Visit` の一覧（復元の入口を兼ねる）

**できること**
- 削除した診察の行から「元に戻す」を押す（`Visit.deleted_at` を消す）
- 履歴の行は読むだけ（直接編集しない）

**満たすべきこと**
- 一覧は日時の降順で、`deleted_at` を持つ `Visit` の変更も含めて漏れなく出る
- 「元に戻す」を押すと、その `Visit` が「本日の患者」「カルテ」等の通常画面に再び出るようになる
- 修正1件につき、変わった項目ごとに「変更前→変更後」がペアで分かる（両方空なら「変更なし」ではなく出さない）

---

### 6. 削除（診察の削除・復元）

**何をする画面か**
1回の診察（`Visit`）を削除する、または削除した診察を戻す。確認ダイアログは使わない専用画面。

**表示するもの**
- 削除（復元）しようとしている `Visit` の要約（診察番号・来院日・診療目的・病名・稟告・現症）
- いま削除済みかどうかの状態

**できること**
- 削除：理由（**必須**）を書いて送信すると `Visit.deleted_at` が入る
- 復元：理由（任意）を書いて送信すると `Visit.deleted_at` が消える

**満たすべきこと**
- 削除は理由が空だと成立しない（保存を拒否し、画面に留まる）
- 削除・復元のどちらも、実行者（`Staff`）と理由が来院履歴に記録される
- 削除しても `Visit` の行・明細（`ProgressNote` 等）は物理的に残っている
- 削除された `Visit` は、カルテ・印刷・検索・来院履歴の通常表示から外れる（来院履歴の「削除した診察」欄には出る）

### 7. 折りたたみ表示

**何をする画面か**
**この企画では扱わないと決めたもの**を1か所にまとめて見せる。個別のボタンを押したときの着地点でもある。

**表示するもの**
- `model.md`「落としたもの」表の全項目（分院・機能の出し分け・役職マスタ・書きかけの自動保存・
  監査ログ・紙カルテ取込・検査/会計/料金の各マスタ編集・レセプト 等）と、それぞれの理由
- 各項目が「この企画のどこで見えるか」（例：分院＝本日の患者の分院欄）

**できること**
- 読むだけ。**この一覧から機能を戻すことはできない**（`model.md` は凍結された契約であり、
  実システムの「機能を畳む／戻す」操作とは別物）

**満たすべきこと**
- `model.md`「落としたもの」表の項目数と、この画面に並ぶ項目数が一致する
- どの項目にも理由の文が空でなく入っている
- 状態Bのボタン（分院・レセプト 等）を押すと、必ずこの画面（またはこの画面内の該当箇所）に着地する

### 8. トップ

**何をする画面か**
この評価版を最初に開いたときの1枚。何ができて、何をこの企画では作っていないかを説明する。

**表示するもの**
- この企画の目的（学習・研究）、5スタックで同じ仕様を実装している旨
- 触れる操作の要約、`model.md` で意図的に外した範囲があること（詳細は「折りたたみ表示」「このシステムについて」へ）
- 中へ入る導線（「本日の患者」一覧へ）
- **対象日の診察件数**（`data-check="visit_count.today"`。「本日の患者」と同じ値）

**できること**
- 「中へ入る」を押すと本日の患者（受付一覧）へ移る

**満たすべきこと**
- 実在の病院名・製品名・ロゴを一切含まない（`coordination/DECISIONS.md` 1章）
- 「できます」と書いた項目は、実際にこの実装で操作できる（状態Aである）
- 合成データのみを使っている旨が明記されている
- `data-check="visit_count.today"` の値が、「本日の患者」画面の同じ値と**完全に一致**する
  （同じ数値を別画面で出しているので、食い違わないことも確認対象）

## 領域2｜診療（5画面）

### 9. カルテ

**何をする画面か**
1回の診察を記録する。過去の診察も同じ画面で遡れる。**印刷しても同じ内容が出ることが前提**。

**表示するもの**
- 患者ヘッダ（カルテNo・動物名・飼主名・種別品種・性別・年齢）
- 表面：来院日・体重・主訴・症状・診断・治療（`Visit`）
- 裏面：経過記録（`ProgressNote` の複数行。日付・体温・脈拍・呼吸・体重・経過・処置・メモ。
  体温・脈拍・呼吸・体重の4値には行ごとに `data-check="progress_note.temperature_c"`
  `pulse` `respiration` `body_weight_kg` を付ける）
- この患者の診察一覧（新しい順。いま開いている回が分かる）

**できること**
| 操作 | 起きること |
| --- | --- |
| 保存 | 表面・裏面の入力を `Visit` / `ProgressNote` として確定する |
| 新しい診察を起こす | 新しい `Visit` を作り、その回を開く |
| 印刷 | いま保存されている内容を印刷用画面（同じ値）で開く |
| 診察の切替 | 一覧から別の回を選んで開く（読み書きは選んだ回に対して行う） |

**満たすべきこと**
- **同じ `Visit` について、画面（`data-check` 4項目）に出ている値と印刷画面の同じキーの値が
  完全一致する**（`data/seed.json` に含まれる全 `Visit` で。1件でも不一致なら不合格）
- `ProgressNote.temperature_c` / `pulse` / `respiration` / `body_weight_kg` は
  **行ごとに保存された値がそのまま出る**。他の行や他の患者の値が紛れ込まない
  （＝別々に入れた値は別々のまま出る。`model.md` にある「全患者に同じ体温が印字された」
  実際の不具合の再発防止。テストは全行を**行単位で**突き合わせる）
- 削除された `Visit`（`deleted_at` あり）は診察一覧にもカルテ本体にも出ない
- 保存後にページを再読み込みしても、保存した値がそのまま出る（消えない・別の回に移らない）

### 10. 検査

**何をする画面か**
検査結果を記録し、基準値との比較を見る。

**表示するもの**
- 患者ヘッダ、検査日・検査カテゴリ（`LabTest`）
- 検査項目ごとの行（`LabTestItem`）：項目名・基準値・単位・結果値
  （結果値には `data-check="lab_test_item.value"`、判定には
  `data-check="lab_test_item.judgment"` を付ける。値は空／`H`（高値）／`L`（低値）のいずれか）
- 基準値・単位は `data/lab_items.json` から、**その患者の種別・性別**で引く（保存はしない）

**できること**
- 検査を新規作成し、項目ごとに結果値（数値または文字）を入力して保存する
- 保存済みの検査を一覧から選んで見る
- 会計へ移る（この患者の会計画面を開く）

**満たすべきこと**
- `value_num` が基準値の範囲外（`min ≦ value_num ≦ max` に**入らない**。両端は範囲内）にある行は、
  `judgment` を `H`（`value_num > max`）または `L`（`value_num < min`）にし、
  同じ要素かその親に `data-check-flag="high"` または `"low"` を付ける。
  範囲内の行は `judgment` を空、`data-check-flag="normal"` にする。
  **判定の文字と色（`data-check-flag`）は独立に確認する**——片方だけ出す実装は不合格
- 対象項目に基準値の組み合わせ（種別・性別）が `data/lab_items.json` に無い場合は、
  判定を付けない（この場合に限り「判定なし」でよい）
- `value_text`（数値以外の結果）の行は判定・色の対象外
- 基準値は `data/lab_items.json` の**現在の値**を使う（この企画では基準値の履歴を持たない）
- 結果値を入力していない項目行も、項目自体は（基準値・単位つきで）表示される
- 「会計」ボタンは、押した患者の会計画面（その患者の保留中の伝票）を開く。行き先が固定の説明文言に飛ばない

## 領域3｜会計・売上（4画面）

### 14. 会計

**何をする画面か**
1枚の伝票（`Billing`）に明細（`BillingDetail`）を積み、金額を確認する。

**表示するもの**
- 伝票ヘッダ：伝票番号（確定前は空）・状態（draft/confirmed）・会計日・患者・飼主
- 明細一覧：分類・コード・内容・単価・数量・課税区分・金額
- **税抜合計・消費税額・税込合計・未算入の行数**（それぞれ `data-check="billing.net_amount"`
  `"billing.tax_amount"` `"billing.total_amount"` `"billing.excluded_count"` を付ける。
  未算入0件でも `excluded_count` の要素は消さず、`0` と表示する）
- 料金項目のピッカー（`data/price_items.json` の分類ごと）

**できること**
| 操作 | 起きること |
| --- | --- |
| 分類から項目を選ぶ | 明細行を1行追加する（数量は指定した値） |
| 明細を複写／削除 | その行を複製／取り消す（`confirmed` の伝票には行えない） |
| 全削除 | `draft` の伝票の明細をすべて取り消す |
| 確定 | 伝票の `status` を `confirmed` にする。以後、明細の追加・削除・複写はできない |
| 履歴へ | この患者の会計履歴を開く |

**満たすべきこと**（金額計算の細目は `acceptance.md`「数値の規則」が正）
- **`unit_price` が未設定の明細行は、どの合計からも0円として含めない。** 除いたうえで合計を出し、
  未算入の行数を併記する
- 計算順序を1つに固定する：①課税対象額＝「課税かつ単価設定済み」の明細の`数量×単価`の合計
  （丸めない）②消費税額＝課税対象額×`Clinic.tax_rate` を**伝票につき1回だけ**円未満切り捨て
  ③税抜合計＝課税対象額＋非課税（`is_taxable=false` かつ単価設定済み）の明細の合計
  ④税込合計＝税抜合計＋消費税額。**明細ごとに税額を計算して積み上げる方式は取らない**
  （行ごとの丸めは実装間で1円単位のズレを生む）
- `status` が `confirmed` の伝票では、明細の追加・複写・削除・全削除がいずれも失敗する
  （画面上は無効表示、APIでも拒否）
- 確定すると伝票番号が採番される（確定前は空）
- 明細が1行も無い伝票は確定できない

### 15. 会計履歴

**何をする画面か**
この動物／この飼主／この病院、3つの範囲で過去の伝票を見る。

**表示するもの**

- 現在開いている動物の行が分かる印（飼主・全体の範囲で他の動物の行と混在するため）

**できること**
- 範囲を切り替える
- 一覧の行から、その伝票を会計画面で開き直す

**満たすべきこと**

## 特に判断が要った箇所

1. **画面と実テンプレートの対応**：`PLAN.md` の26画面ラベルと、題材の24テンプレート＋新2画面は
   厳密な1対1の一覧が存在しなかった。特に「トップ」＝表看板（評価版の入口）、
   「このシステムについて」＝**この企画自身**の説明（題材の表看板とは別物）、
   「来院履歴」＝修正履歴画面、「書類」＝紙カルテPDF画面、と読み替えた。印刷画面は
   独立の1画面に数えず、「カルテ」画面の一機能（印刷モード）として扱った
2. **「折りたたみ表示」の再定義**：題材では病院ごとに機能を畳む／戻すライブ機能だったが、
   その元になる `ClinicFeature` モデル自体を `model.md` で落としている。そのため
   この契約では**動的な出し入れ機能ではなく、「この企画では扱わない」ことの静的な一覧**に
   作り替えた。「機能設定」画面も同じ元データを参照する読むだけの画面にした
3. **本日の患者の枠A・枠B**：診察・会計・検査・入院/ホは本企画のモデルに対応先があるため
   状態Aとしたが、調剤・処置・手術・トリミング・備考・分院には対応するモデルが無いため、
   すべて状態B（この企画では扱わない）とした
4. **入院画面の作り直し**：題材は診察（Visit）ベースの日誌形式だが、`model.md` の
   `Hospitalization` は在室情報とケア記録（実施者必須）を持つ別モデルとして定義されている。
   この契約では後者の形で設計し、実施者必須の検証を明記した
5. **売上集計の集計基準**：`Billing.status = confirmed` のみを対象とし、`draft`（未確定）は
   売上に含めないと決めた。分類・担当・日付の3表が同じ総額になることを検証条件にした
6. **予約は1画面**：`PLAN.md` の画面数（26）に合わせ、一覧と新規作成・編集を1つの画面
   （スケジュール表＋インライン操作）としてまとめた。`patient_id` は必須とし、
   飼主が決まっていない電話予約（題材にはある）はこの契約のスコープ外とした
7. **認証は扱わない**：`coordination/DECISIONS.md` の決定に従い、「スタッフ」画面は
   パスワード認証ではなく担当者の申告のみとした。`model.md` の `Staff.password_hash` は
   保存衛生（平文で持たない）だけを検証対象とし、ログイン画面自体は設けていない
