# 受け入れ条件 — 検算

**この文書が「5つの実装が正しいと言える条件」である。** `spec/README.md` の完了の判定 2 に
ある「検算がすべて一致する」の中身がここに書いてある。

## この文書の考え方

テストが緑になっても、それは「テストが検証した範囲で合っている」ことしか意味しない。
2026-09-05 の別プロジェクトでは、テストが緑のまま**テストの期待値そのものが誤っていた**
（`json_encode(5.0)` が `5` に正規化されることを知らずに期待値へ `5.0` と書いていた）。

そこでこの文書は、**実装のコードを1行も読まずに、出てきた数字だけで正誤を判定できる条件**
を定義する。中心になる考え方は1つ。

> **同じ数字を、違う経路で出して突き合わせる。**
> 1つの経路の答えだけを見ても、その経路が正しいことしか分からない。
> 分類別・担当別・日別のように**別々のコードパスで計算した合計が一致する**ことは、
> 双方に同じ間違いが同時に起きない限り、単独チェックより強い証拠になる。

**「おおむね」「適切に」「十分に」は使わない。** 確かめられない条件は条件ではない。
各項目の「合格の条件」は必ず数値・真偽値・件数で書く。

## 表記の規則

- **金額**: 特記なき限り日本円。整数円。
- **日付**: `YYYY-MM-DD`。**時刻境界はすべてJST**（集計の月境界もJST）。
  日時型（`received_at` / `starts_at` / `ends_at` / `deleted_at` など）は保存形式が
  UTCであってもJSTへ変換してから日付境界を判定する。日付型（`billed_on` / `visit_date` など）
  はJSTの暦日として扱う（タイムゾーン変換は発生しない）。
- **文字数**: Unicodeコードポイント数で数える。**バイト数で数えない**（UTF-8では日本語1文字が
  3バイトになり、バイト数で数えると実際より短い制限になる）。
- **期間**: 「対象期間」とは、検算を行う `from`〜`to`（両端を含む、JSTの暦日）を指す。
  テストが期間を指定しない場合は `data/seed.json` が持つ全期間を対象期間とする。

## 数値の規則

### 丸め — どこで、何回丸めるか

| 対象 | 規則 |
| --- | --- |
| 明細小計（`quantity × unit_price`） | **丸めない。** 内部計算は小数のまま保持する |
| 伝票の税抜合計・税込合計 | **表示する最後の1回だけ**、円未満を切り捨てて整数円にする |
| 消費税額 | 下記「消費税の計算順序」のとおり、**伝票ごとに1回だけ**円未満を切り捨てる |
| 構成比（%） | 小数第1位までを**最大剰余法**で丸める（下記） |
| 上記以外の数値 | **丸めない**（`spec/README.md` の原則どおり、書いていない丸めは行わない） |

**丸めた値を再度合計しない。** 先に行ごとに丸めてから合計すると、丸め誤差が積み上がって
合計がずれる（実際によくある不具合）。集計は**丸める前の値を足し、最後に1回だけ丸める。**

### 消費税の計算順序（1つに決める）

1. 伝票（`Billing`）ごとに、`is_taxable = true` かつ `unit_price` が設定されている明細の
   `quantity × unit_price` を合計する（＝その伝票の**課税対象額**。丸めない）。
2. 課税対象額 × `Clinic.tax_rate` を計算し、**円未満を切り捨てる**（＝その伝票の**消費税額**）。
   この切り捨ては**伝票につき1回だけ**行う。明細ごとに税額を計算して合計する方式は取らない
   （明細ごとに切り捨てると、伝票内で切り捨て誤差が明細数ぶん積み上がり、実装によって
   1円単位でずれるため。5実装を1円単位まで一致させるには、丸め回数を1回に固定する必要がある）。
3. 税抜合計 = 課税対象額 ＋ 非課税明細（`is_taxable = false` かつ `unit_price` 設定あり）の合計。
4. 税込合計 = 税抜合計 ＋ 消費税額。
5. `unit_price` が未設定の明細は、上記のどの合計にも**含めない**（検算2）。

> **この順序は仕様として固定する。** 実装が独自の順序（例: 明細ごとに税込金額を計算してから
> 合計する）を採ると、消費税額が1円単位でずれ、5実装の答えが割れる。

### 構成比の丸め（最大剰余法）

分類別の構成比は「小数第1位まで表示して、合計が必ず100.0%になる」必要がある。
単純に四捨五入すると合計が99.9%や100.1%になり得るため、次の手順で丸める。

1. 各分類の構成比の素の値 `raw_i = 分類iの税抜合計 ÷ 対象期間の税抜合計 × 100` を計算する。
2. `raw_i` を小数第1位で切り捨てた値 `floor_i` を仮の値とする。
3. `100.0 - Σ floor_i` を `0.1` で割った件数ぶん、**剰余（`raw_i - floor_i`）が大きい分類から順に**
   `floor_i` に `0.1` を1回ずつ足す。
4. 対象期間の税抜合計が0円のときは、この検算自体を対象外とする（分母が0のため）。

### タイムゾーンの根拠

この業務は国内1施設の窓口業務であり、複数タイムゾーンを扱う要件が無い。JSTに固定して
実装間の差を無くす（`coordination/DECISIONS.md` 第4節と同じ）。

## 共通の確認手段

以下の検算は「人が画面を見て確かめる」のではなく、次の3つの手段のどれかで機械的に確認する。
26画面を目視で確認するのは不可能であるため（`spec/README.md`）。

### 手段A：JSON API（`spec/openapi.yaml`）

数値の正しさそのもの（合計・件数・判定）は、可能な限り**JSONレスポンスの値**で確認する。
`spec/openapi.yaml` は、この文書が要求する値をエンドポイントのレスポンスに含めること
（例：会計のレスポンスに税抜合計・消費税額・未算入件数を持たせる、検査項目のレスポンスに
判定 `judgment` を持たせる、等）。**どのエンドポイントに何を持たせるかは `openapi.yaml` 側で
定義する。この文書は「その値が満たすべき条件」だけを定める。**

### 手段B：`data-check` 属性（画面の表示そのものを確かめる必要がある場合）

検算3（固定値）・検算4（印刷一致）・検算5（範囲外表示）は、**APIの値が正しくても
画面のテンプレートが間違って表示する**不具合を狙っている（実際に起きた不具合が検算3）。
そのため画面のHTMLそのものを機械的に読む必要がある。

見た目（CSS・レイアウト・文言）は各スタックの流儀でよいが（`spec/README.md`）、
下表の項目には**見えない目印として** `data-check="<キー>"` 属性を持つ要素で値を囲むこと。
これは見た目に影響しない（属性はレンダリングされない）ため、「見た目は自由」の原則と両立する。

| キー | 意味 | 現れる画面 |
| --- | --- | --- |
| `billing.net_amount` | 伝票の税抜合計 | 会計・会計履歴・その印刷 |
| `billing.tax_amount` | 伝票の消費税額 | 同上 |
| `billing.total_amount` | 伝票の税込合計 | 同上 |
| `billing.excluded_count` | 未算入の明細行数 | 同上 |
| `progress_note.temperature_c` | 経過記録の体温 | カルテ・その印刷 |
| `progress_note.pulse` | 経過記録の脈拍 | 同上 |
| `progress_note.respiration` | 経過記録の呼吸数 | 同上 |
| `progress_note.body_weight_kg` | 経過記録の体重 | 同上 |
| `lab_test_item.value` | 検査項目の値 | 検査 |
| `lab_test_item.judgment` | 検査項目の判定（空 / `H` / `L`） | 検査 |
| `sales_summary.net_amount` | 売上集計の行合計（属性 `data-check-axis`＝`category`\|`staff`\|`date`\|`total`、`data-check-key`＝分類名・スタッフID・日付のいずれか。総合計行は `data-check-axis="total"`） | 売上集計 |

### 手段C：クローラー（検算8専用）

`tests/` に、HTTP経由でリンクを辿る共通クローラーを1本用意する（実装言語を問わない）。
起点はトップ画面。詳細は検算8に書く。

## 検算1：売上の3方向一致

**何を確かめるか**: 対象期間の税抜売上合計を「分類別」「担当別」「日別」の3つの切り口で
集計し、それぞれの内訳の合計が、対象期間全体の税抜売上合計と一致することを確かめる。

**なぜ必要か**: 3つの切り口は実装上ふつう別々のクエリ・別々のコードパスになる。
「担当別だけ `cashier_staff_id` ではなく `staff_id` で絞っている」「日別だけ `billed_on` ではなく
伝票の作成日時で絞っている」「分類別だけ `status = confirmed` の絞り込みが漏れている」
といったズレは、単独の合計を見ているだけでは気づけない。3方向を突き合わせて初めて検出できる。

**前提となる定義**:

- 対象は `Billing.status = "confirmed"` の伝票のみ（`draft` は除外）。
- 各明細のうち `unit_price` が未設定の行は、金額・構成比のどちらの計算からも除外する（検算2）。
- 税抜売上 = 明細の `quantity × unit_price` の合計（丸めない。「消費税の計算順序」参照）。
- **分類**は `data/price_items.json` の各料金項目が持つ上位1階層の分類
  （`model.md` にある「分類（2階層）」のうち上位側。以後 `category_major` と呼ぶ）。
- **担当**は `Billing.staff_id`（診療担当）を使う。`cashier_staff_id`（会計処理を行った人）
  は使わない（この判断は末尾「判断が割れそうな箇所」に記載）。
- **日別**は `Billing.billed_on`（JSTの暦日）で区切る。

**どう確かめるか**:

1. `data/seed.json` を独立に読み込み（実装のコードを経由せず）、上記の定義に従って
   期待値（分類別内訳・担当別内訳・日別内訳・総合計）をテストコード側で計算する。
2. 実装のAPI（`spec/openapi.yaml` の売上集計エンドポイント）へ同じ対象期間を渡して
   3つの内訳と総合計を取得する（取得できない場合は `data-check-axis` 付きの画面から
   手段Bで読む）。
3. 実装が返した「分類別の合計を全部足した値」「担当別の合計を全部足した値」
   「日別の合計を全部足した値」「総合計」の4値を比較する。
4. 併せて、手順1で計算した期待値と、実装が返した総合計を比較する
   （内訳同士が一致しても、全体がそもそも間違っていたら意味が無いため）。

**合格の条件**:

- 上記4値が**完全に一致**する（円未満は生じない。税抜売上は最後に1回だけ丸めるため、
  総合計と内訳合計はいずれも同じ丸め処理を1回受けた値同士の比較になる）。
- 実装の総合計が、テストコードが独立に計算した期待値と一致する。
- 分類別の構成比（`sales_summary.share_pct`）の合計が **厳密に100.0**（最大剰余法適用後）。
  ただし対象期間の税抜売上合計が0円の場合はこの構成比チェックを対象外とする。

**消費税額について（この検算に含めないこと）**: 消費税は伝票単位で1回だけ切り捨てるため
（「消費税の計算順序」）、分類別・担当別に消費税額を按分すると按分方法によって答えが変わり、
検算にならない。したがって**3方向一致の対象は税抜売上のみ**とする。税込の総額については、
「対象期間の税抜合計＋対象期間の全伝票の消費税額の合計＝対象期間の税込合計」という
1本の等式のみを確認する（3方向へは分解しない）。

## 検算2：未算入の明示

**何を確かめるか**: `unit_price` が未設定の明細行が、金額の合計に0円として含まれていないこと。
また、含めなかった行数（未算入件数）が画面またはAPIに明示されていること。

**なぜ必要か**: 題材の実システムで実際に発生した不具合。単価未設定の行を0円として合計に
含めていたため、**エラーは出ないが実際より少ない合計が表示され続けていた**。
合計を非表示にするのは対処にならない（次に何をすべきか分からなくなるため、
`spec/README.md`）。合計は出したうえで、未算入件数を必ず併記させる。

**どう確かめるか**:

1. `data/price_items.json` には単価未設定の項目が意図的に含まれる（`spec/README.md`）。
   `data/seed.json` の会計明細のうち、その項目を使っている行を独立に数え上げ、
   件数 `N` と、それらを除いた場合の正しい税抜合計 `E` をテストコード側で計算する。
2. 実装のAPI（またはBの `billing.net_amount` / `billing.excluded_count`）から、
   同じ伝票の税抜合計と未算入件数を取得する。
3. 取得した税抜合計が `E` と一致し、未算入件数が `N` と一致することを確認する。
4. `unit_price` 未設定の行がある伝票について、`billing.excluded_count` に対応する
   `data-check` 要素が**存在すること**（値が0のときに要素ごと消えていないこと）も確認する。

**合格の条件**:

- 税抜合計が `E` と完全一致（未算入行を1円も含めていない）。
- 未算入件数が `N` と完全一致。
- `N > 0` の伝票では、画面上に未算入件数を示す要素が存在し、値が `N` と一致する。
- `N = 0` の伝票では、未算入件数の表示は `0`（要素の非表示ではなく、0件と分かる表示）。

## 検算3：固定値が現れない

**何を確かめるか**: `ProgressNote` の `temperature_c` / `pulse` / `respiration` /
`body_weight_kg` が、患者・診察ごとに記録した値のとおりに、その行の表示として出ること。
他の行の値がそのまま出ていないこと。

**なぜ必要か**: 題材の実システムで実際に起きた不具合。**全患者のカルテに同じ体温が印字**
されていた（テンプレートに固定値がそのまま残っていた）。印刷の点検が「用紙からはみ出して
いないか」に寄っていて、値そのものの正しさが点検対象に入っていなかった。

「全部が同じ値でないか」だけを見る検査では、たまたま2種類の値が交互に出ているだけでも
不具合を見逃す。**行ごとに、その行の値と完全一致するか**を確認する方式にする。

**どう確かめるか**:

1. `data/seed.json` の `ProgressNote` には、**異なる患者にまたがって
   `temperature_c` が5種類以上の異なる値**を持つ行を含める（データ側の要件。
   `pulse` / `respiration` / `body_weight_kg` も同様に3種類以上の異なる値を含める）。
   これが無いと、固定値化されていても偶然一致して不具合を見逃しうる。
2. `data/seed.json` に含まれる**全ての** `ProgressNote` 行について、対応するカルテ画面
   （`patient.karte_no` で特定される）から `data-check="progress_note.temperature_c"` 等の
   値を読む。
3. 読んだ値と、`data/seed.json` のその行の値を**行単位で**突き合わせる
   （「他のどこかの行の値と一致していないか」ではなく「自分の行の値と一致しているか」）。

**合格の条件**:

- `data/seed.json` に存在する `ProgressNote` の**全行**について、画面の表示値が
  ソースの値と完全一致する（4項目とも）。1行でも不一致があれば不合格。
- 上記1のデータ要件（5種類以上／3種類以上）を `data/seed.json` が満たしていることも
  この検算の前提条件としてテストの冒頭で確認する（満たさない場合はテスト自体が不正）。

## 検算4：画面と印刷が一致

**何を確かめるか**: カルテと会計について、通常の画面表示と印刷表示で、同じ項目に同じ値が
出ること。

**なぜ必要か**: 印刷は別テンプレート（別ルート・別コンポーネント）になりがちで、
通常画面を直したときに印刷側の反映を忘れる、あるいは印刷側だけ古い計算式が残る、
という食い違いが起きやすい。検算3と同じ「テンプレート側の不具合」を印刷経路でも狙う。

**どう確かめるか**:

1. 対象は次の項目（いずれも「共通の確認手段」表の `data-check` キー）。
   - カルテ: `progress_note.temperature_c` / `pulse` / `respiration` / `body_weight_kg`
   - 会計: `billing.net_amount` / `billing.tax_amount` / `billing.total_amount` /
     `billing.excluded_count`
2. 同一のレコード（同じ `visit_id` または同じ `billing_id`）について、通常画面のレスポンスと
   印刷用画面のレスポンス（URLの区別方法は `spec/openapi.yaml` が定める）の両方を取得する。
3. 双方から同じキーの `data-check` 要素のテキストを読み、桁区切りのカンマ・前後の空白を
   除去したうえで文字列として比較する。
4. `data/seed.json` に含まれる**全ての** `Visit` と `Billing` について実施する
   （一部だけの抜き取りにしない。件数はテストコードが `seed.json` から数える）。

**合格の条件**:

- 全レコード・全項目で、通常画面の値と印刷の値が完全一致する。
- 一致しないレコードが1件でもあれば不合格。不合格のときはテストが**どのレコードの
  どの項目で**不一致だったかを出力する（全体がNGとだけ言って終わらない）。

## 検算5：検査の範囲外表示

**何を確かめるか**: `LabTestItem.value_num` が `data/lab_items.json` の基準値の範囲外に
あるとき、**判定欄（テキスト）と色（状態）の両方**に出ること。範囲内のときはどちらも
出ないこと。

**なぜ必要か**: 判定欄だけに出て色が付かない、あるいは色だけ付いて判定の文字が出ない、
という半端な実装は見落としの原因になる（窓口業務では色だけを見て判断することがあるため）。
両方を独立に確認する。

**基準**: `data/lab_items.json` の基準値は検査項目・種別・性別の組み合わせで決まる
（`model.md`）。基準の下限を `min`、上限を `max` とする。

- `min ≦ value_num ≦ max` のとき「範囲内」（**両端を含む**。ちょうど境界値は範囲内）。
- それ以外（`value_num < min` または `value_num > max`）のとき「範囲外」。
  `value_num < min` なら低値（`L`）、`value_num > max` なら高値（`H`）。
- 対象項目に基準値が定義されていない場合（`lab_items.json` に組み合わせが無い）は、
  この検算の対象から除外する（判定なしを不合格としない）。
- `value_text`（数値以外の結果）の行はこの検算の対象外。

**どう確かめるか**:

1. `data/seed.json` の `LabTestItem` から、独立に「範囲内」「範囲外（高値）」
   「範囲外（低値）」の3グループそれぞれ1件以上を含むデータであることを確認する
   （3グループとも無いと、この検算は意味を成さない）。
2. 各グループの行について、`data-check="lab_test_item.judgment"` の値
   （空 / `H` / `L`）を読む。
3. 同じ要素（またはその親要素）に `data-check-flag` 属性
   （`normal` / `high` / `low`）が付いていることを確認する。
   **色そのもの（CSSの具体的な色コード）の一致は問わない**（見た目は各スタックの流儀でよい
   ため）。`data-check-flag` は色分けの根拠になる状態を機械的に示す目印として扱う。

**合格の条件**:

- 範囲内の行: `judgment` が空、`data-check-flag` が `normal`。
- 範囲外（高値）の行: `judgment` が `H`、`data-check-flag` が `high`。
- 範囲外（低値）の行: `judgment` が `L`、`data-check-flag` が `low`。
- 境界値（`value_num = min` または `value_num = max`）の行が `data/seed.json` に
  少なくとも1件あり、それが「範囲内」判定になっていること。

## 検算6：予約の重なりが無い

**何を確かめるか**: `status = "booked"` の予約について、同じ担当（`staff_id`）同士、
および同じ処置室（`room`）同士で、時間帯が重ならないこと。

**なぜ必要か**: 予約は新規画面（`model.md` の「落としたもの」に無い、この企画で新設する画面）。
重複判定はデータ全体を突き合わせないと見つからない典型例であり、目視での確認は不可能。

**重なりの定義**: 2つの予約 `(starts_at1, ends_at1)` と `(starts_at2, ends_at2)` が
重なるとは、`starts_at1 < ends_at2` かつ `starts_at2 < ends_at1` が成り立つこと
（半開区間として扱う。**片方の終了時刻ともう片方の開始時刻がちょうど一致するのは
重なりに含めない**。例えば10:00–10:30の次に10:30–11:00を予約できる）。

**どう確かめるか**:

1. `status = "booked"` の予約全件（`data/seed.json` 由来のもの、および
   テストが新規作成したもの）を取得する。
2. `staff_id` ごとにグループ化し、各グループ内を `starts_at` で昇順に並べ、
   隣り合う予約同士が上記の定義で重ならないことを確認する（ソート済みなら隣接ペアの
   確認だけで全ペアを検査したことになる）。`room` についても同様に行う。
3. 既に埋まっている時間帯・担当・処置室に対して、重複する新規予約の作成をAPI経由で
   試み、**拒否されること**（成功してしまわないこと）を確認する。拒否時のステータス
   コード・エラー文言は `spec/openapi.yaml` の定義に従う。この検算では
   「登録が失敗し、既存の予約件数が作成前後で変化しないこと」を必須条件とする。
4. `status = "cancelled"` の予約は重なり判定の対象外であることを確認する
   （キャンセル済みの時間帯には新規予約が作成できる）。

**合格の条件**:

- `staff_id` ごと・`room` ごとに、重なりが**0件**。
- 重複する予約の新規作成が拒否され、かつ拒否後の予約件数が拒否前と同じ。
- キャンセル済みの時間帯への新規予約が成功する。

## 検算7：入院記録の実施者

**何を確かめるか**: 入院（`Hospitalization`）の `care_records`（投薬・給餌・計測の記録行）に、
実施者が空の行が無いこと。

**なぜ必要か**: `model.md` に明記のとおり、誰が実施したか分からない記録は記録として成立しない。
この文書では `care_records` の各要素が持つ実施者のフィールドを `performed_by_staff_id`
（`Staff.id` への参照、必須）と定める。

**どう確かめるか**:

1. `data/seed.json` の入院データに含まれる `care_records` の全行を取得し、
   `performed_by_staff_id` が非null、かつ `data/seed.json` の `Staff` に実在する
   `id` を指していることを確認する。
2. 画面上でも `data-check="care_record.performed_by"` の要素のテキストが
   空でないことを、全行について確認する。
3. `performed_by_staff_id` を指定せずに記録行を作成するAPI呼び出しを試み、
   **拒否されること**を確認する（ステータスコード・文言は `spec/openapi.yaml` に従う）。
   拒否後、その入院の記録件数が呼び出し前と変化していないこと。

**合格の条件**:

- `data/seed.json` 由来・テスト作成分を問わず、実施者が空の記録行が**0件**。
- 実施者を指定しない作成が必ず拒否され、記録件数が変化しない。

## 検算8：死んだリンクが無い

**何を確かめるか**: 26画面（＋新規2画面）のいずれからリンクされているページも、
実際に開けること（404・500にならないこと）。

**なぜ必要か**: 画面数が多く、目視での全数確認は現実的でない（`spec/README.md`）。

**どう確かめるか**:

1. `tests/` の共通クローラーが、トップ画面を起点に幅優先探索を行う。
2. 探索対象は同一オリジンの `<a href>` と、GETで到達できるフォームの `action` 先。
   `mailto:` / `tel:` / `javascript:` / 外部ドメイン / `#` のみのフラグメントは対象外。
3. 到達した各URLに対して1回GETし、レスポンスのステータスコードを記録する。
4. `karte_no` や `slip_no` のようにIDに依存する画面は、`data/seed.json` に存在する
   IDのぶんだけ辿る（存在しないIDへの遷移リンクが無いことも兼ねて確認する）。

**合格の条件**:

- 到達した全URLのステータスコードが200番台。
- 到達したURL（テンプレート単位で重複を除いたもの）の種類数が、26＋2＝**28画面分以上**
  （網羅漏れがあると「リンクが無いから壊れていないように見える」誤検知になるため、
  クロールの網羅性そのものをこの数値で担保する）。
- レスポンス本文に、一般的なサーバーエラー表示（スタックトレース・
  `Internal Server Error` 等の文字列）を含む200番台の応答が無いこと
  （ステータスは200でも中身がエラー画面という状態を防ぐ）。

## 検算9：消したものが数に残る

**何を確かめるか**: `Owner` / `Patient` / `Visit` の `deleted_at` に日時が入った行が、
一覧からは既定で消えつつ、**集計（件数・金額）からは消えない**こと。

**なぜ必要か**: `model.md` に明記のとおり、物理削除すると「その日に何件診たか」が
数えられなくなる。削除は一覧表示から隠すだけの操作であり、実績としては残り続ける
必要がある。

**どう確かめるか**:

1. 対象日に `Visit` を1件新規作成し、その日の診察件数（`data-check="visit_count.today"`）
   を取得して基準値 `V` とする。
2. 作成した `Visit` の `deleted_at` に日時を設定する（削除する）。
3. 一覧（既定表示）を取得し、その `Visit` が**含まれていない**ことを確認する。
4. 一覧の「削除済みも表示」を選んだ状態で取得し、その `Visit` が**含まれている**ことを
   確認する。
5. 削除後の対象日の診察件数を再取得し、`V`（削除前の件数）と**変化していない**ことを
   確認する。
6. `Owner` / `Patient` についても、手順1・5に相当する「一覧から消えても、紐づく
   `Visit` / `Billing` の実績（件数・金額）は変化しない」ことを確認する
   （例: `Patient` を削除しても、その患者の過去の売上が売上集計の対象合計から消えない）。

**合格の条件**:

- 削除直後、既定の一覧に対象行が現れない。
- 「削除済みも表示」を選ぶと対象行が現れる。
- 削除の前後で、日次診察件数・売上集計の対象合計のいずれも**完全に同じ値**のまま
  （1件・1円も変化しない）。

## 判断が割れそうな箇所（報告）

以下は `spec/model.md` に明記が無く、この文書を書く上で決めが必要だったため、
自分の判断で決めたもの。他レーンの解釈と食い違う可能性があるので指揮役の確認を推奨する。

1. **検算1の「担当」軸に `Billing.staff_id` を採用し、`cashier_staff_id` を使わなかった**。
   `model.md` はこの2つの使い分けを書いていない。売上を「診療した担当」で見る前提で決めたが、
   「会計処理をした担当」で見る想定だった場合は軸が変わる。
2. **`price_items.json` の2階層分類のうち、上位1階層（`category_major`）だけを
   売上集計の分類軸に使うと決めた。** 下位階層は使わない。
3. **消費税は伝票単位で1回だけ切り捨て、明細ごとの按分計算はしないと決めた。**
   分類別・担当別の内訳には消費税を含めず、税抜売上のみで3方向一致を取る設計にした。
   もし売上集計画面が「税込」で分類別に出す想定だった場合、按分方法を別途決める必要がある。
4. **`data-check` / `data-check-axis` / `data-check-key` / `data-check-flag` という
   HTML属性の目印を、この文書が新規に定義した。** `spec/screens.md` や
   `spec/openapi.yaml` が独自の確認手段（別の属性名など）を前提に書かれていた場合、
   どちらかに合わせて統一する必要がある。
5. **`Hospitalization.care_records` の実施者フィールド名を `performed_by_staff_id` と
   決めた。** `model.md` にはフィールド名の記載が無かったための命名。
6. **検算6の重なり判定を半開区間（終了時刻＝次の開始時刻は重なりとしない）と決めた。**
   窓口業務の慣習に合わせたが、明示の合意ではない。
