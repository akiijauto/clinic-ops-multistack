### R-20 Rails: `Api::ReservationsController` に `create`/`show`/`update`/`cancel` が無い（画面側は別で実装済み） 【重い】

**どこで**: `stacks/rails/app/controllers/api/reservations_controller.rb`（`index` のみ）、
対して `stacks/rails/config/routes.rb:166-169`（`namespace :api` 配下に `create`/`update`/`cancel` のルートが定義済み）

**何が**: ルートは存在するのに、その行き先のメソッドが無い。JSON APIとしての予約作成・変更・
取消は**すべて404**になります。

**紛らわしい点（誤解しないよう明記）**: 画面（`/reservations` 等、`ReservationsController`
という**別クラス**）は `create`/`update`/`cancel` を全部実装済みで、画面からの登録は動きます
（下記の「押しても何も起きるが、その後に問題がある」参照）。**JSON APIだけが未実装**です。

### R-22 FastAPI: `POST /api/reservations` が、タイムゾーン付き日時（`+09:00`）を渡すと500でクラッシュする。しかもこの形式は契約の正データそのもの 【重い・優先度高】

**どこで**: `stacks/fastapi/app/routers/reservations.py` の `create_reservation`（Pydantic の
`ReservationCreate.starts_at: dt.datetime` がタイムゾーン付き文字列をaware datetimeとして
受け取り、SQLite/SQLAlchemyへ書き込む際に例外を起こしていると見られる）

**確かめたこと**（2回、条件を変えて再現）:

```
starts_at="2099-01-01T09:00:00+09:00"  → 500 Internal Server Error
starts_at="2099-02-01T10:00:00"        → 201 正常に作成（オフセット無しなら通る）
```

**なぜ重いか**: `data/seed.json` の予約データは**全件このオフセット付き形式**です
（例：`{"starts_at": "2026-09-01T09:00:00+09:00", ...}`）。`spec/acceptance.md`
「タイムゾーンの根拠」でJSTに固定すると決めているので、**正しい書き方をしたクライアントほど
このバグを踏みます。** ブラウザの `datetime-local` 入力はオフセット無しの文字列を送るため、
FastAPI自身の画面フォームからの登録では踏まないと見られますが、
**JSON APIを正しく契約どおりに使うクライアントは必ず踏みます。**

**担当**: レーンD

## 見つけたもの：Rails予約画面は、実際に登録できるが、51件目以降が画面から二度と見えなくなる 【中〜重い】

**押しても何も起きない画面**ではなく、**押すと起きるが、その後に見えなくなる**型です。
順を追って確認しました（`stacks/rails/app/controllers/reservations_controller.rb` の画面側）。

1. `/reservations/new` から実際にフォームを送信（CSRFトークンを画面から取得し、
   ブラウザと同じ形で `POST /reservations` を送信）
2. 応答に `data-testid="success-banner"` が現れ、文言は「予約を登録しました。」
3. `GET /api/reservations` で確認すると、**送信した内容がそのまま保存されている**
   （id・患者・時刻・担当・処置室・目的、すべて一致）
4. しかし `/reservations` の一覧画面には**出てこない**

**原因**: `app/controllers/reservations_controller.rb` の `index`:

```ruby
def index
  @date = params[:from].present? ? Date.parse(params[:from]) : Date.current
  @reservations = Reservation.includes(:patient, :staff).order(:starts_at).limit(50)
end
```

`@date` を計算しているのに**`@reservations` の絞り込みに一度も使っていません。**
`.limit(50)` だけが効いており、`starts_at` 昇順で**先頭50件**を常に返します。

**実測**: `?from=2024-01-01` と `?from=2099-01-02` を実行すると、**返るHTMLがバイト単位で
完全に同一**でした（`md5sum` 一致）。一覧には常にちょうど50行（`data-testid="row-reservation"`）
が出て、ページ送り・並べ替えのUIはありません。

現在の総件数は62件（元60件＋今回の確認で作った2件）。**新しく作った予約（`starts_at` が
2099年）は、`starts_at` 昇順で最後尾に来るため、先頭50件から外れて一覧から一生見えません。**
日付を変えても同じ50件が出るだけなので、ユーザーには「登録した予約が消えた」ように見えます。

**契約との関係**: `spec/screens.md` #19「できること」に
「**日付を切り替えて別の日の予約を見る**」とあります。Rails画面には**その切り替えUI自体が
まだ無く**（`type="date"` の入力欄が見当たらない）、`from` パラメータは受け取るコードだけが
先にあってフィルタが未実装、という状態です。**「日付を切り替える」機能そのものが
まだ存在しないので、いまは"嘘をついている画面"ではなく"未着手の機能"に近い形**ですが、
`limit(50)` の副作用（新しい予約が一覧から消える）は**画面の見た目に嘘が無くても実害がある**
ため、別途報告します。

**担当**: レーンB

## 参考：Laravel・Rails とも「画面からの登録」自体は実際に動く（確認済み）

上記の欠陥はどちらも**JSON APIの経路**にあります。**画面のフォームからの登録は、
Laravel・Railsとも実際に動作すること**を、ブラウザと同じ手順（フォーム取得→CSRFトークン→
POST）で確認しました。Laravelは62件目の予約として実際にDBへ保存されたことをAPIで確認済みです。
**「押しても何も起きない画面」ではありません。** 分けて報告するのは、
JSON API（契約の正）と画面（各レーンの実装）が食い違っているのを紛れさせないためです。
