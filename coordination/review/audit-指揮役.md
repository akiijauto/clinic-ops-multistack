## 2. 「契約の画面42件・API36件がすべて在る」— 「確かめられない」を「在る」に含めている

**指揮役の主張**: 42画面・36APIすべてが実在する。

**示された根拠**: `tests/run.py --only inventory` の実測（40/42画面・35/36API）と、
各レーンが過去に個別のpaper IDへcurlして200を確認したという報告。

**根拠が届いていない範囲**: 78件中3件（`/papers/{paper_id}` `/papers/{paper_id}/remove`
`/api/papers/{paper_id}`）は自動検査が「確かめられない」と分類したままで、**「在る」に
分類されたことは一度も無い**。「すべて在る」という言い方は、この3件を含めて言っている
のか、含めずに言っているのかが区別できない書き方になっている。

**実測**（11:41、5実装すべてへ `/papers/1` をGET）:

| 実装 | `/papers/1` |
| --- | --- |
| Go | 404 |
| Rails | **200** |
| Laravel | 404 |
| FastAPI | 404 |
| Next.js | 404 |

**5実装中4つで404。** 「レーンCが以前curlで200を確認した」という過去の報告は、
その時点でそのレーンが手動でpaperを1件作成した後の状態を指しており、**今のサーバー
状態では再現しない**（サーバー再起動やデータ再シードで消えたと見られる。原因は未確認）。
一覧画面（`/animals/{karte_no}/papers`）と一覧API は5実装とも200で問題ない。

**どう直すか**: 「画面42・API36がすべて在る」ではなく「75/78件は確認済み、papers個別
表示・削除の3件は未確認（実装ごとにデータ状態が揃っておらず、自動検査もその場のcurlも
再現性が無い）」と書く。既知の限界として残すなら`rulings.md`に一言残すこと（R-21で
papersを範囲内と裁定した際、個別ページの動作確認手段が無いことまでは裁定していない）。

## 3. 「共通CSSを5実装が配り、全画面が読んでいる。中身は完全一致」— CSSの一致は実測で確認、「全画面」は主張2と同じ穴を持つ

**指揮役の主張**: 5実装が`/ui.css`を配布し、全画面が読み込み、中身は完全一致。

**示された根拠**: `tests/run.py --only inventory` の「見た目」検査（各レーンで
「NN画面すべてが読んでいる」）。

**実測で確認できた部分**（このレーン独自に実施、根拠が届いている）:
- 5実装すべての`/ui.css`を`spec/ui.css`と`diff`し、**バイト単位で完全一致**を確認
- papers一覧画面（`inventory.py`の自動検査の対象外）でも5実装すべてが`ui.css`を
  読み込んでいることを個別に確認

**根拠が届いていない範囲**: `tests/inventory.py`の「見た目」検査は`_resolve()`が
埋められる画面だけを数えている。主張1・2と同じ理由で、**papers詳細・remove確認の
2画面は「全画面」の実測対象に一度も入っていない**。今のサーバー状態では該当ページに
到達できるのが5実装中1つ（Rails）のみで、残り4つは確認しようがない。

**どう直すか**: 「全画面が読んでいる」を「42画面中40画面で確認、papers詳細・remove
2画面は未確認」に直す。CSSの中身の一致は胸を張ってよい（実測で裏付けが取れている）。

## 5. 「見た目が揃った」— 意味の範囲が書かれていない

**指揮役の主張**: 見た目が揃った。

**示された根拠**: 共通CSS配布・指定クラスの出現確認（主張3の検査）。

**根拠が届いていない範囲**:
1. `coordination/qa/rulings.md`冒頭・`DECISIONS.md`には**既存の裁定**として
   「画面の見た目は各スタックの流儀でよい。揃えるのは振る舞いだけ」と明記されている。
   今回のCSS配布がこの裁定を**更新したのか、単に上乗せしただけなのか**が
   `rulings.md`に新しい裁定として書かれていない。「見た目が揃った」と言うなら、
   古い裁定とどう両立するのかを一言残す必要がある
2. 「揃った」の中身は「共通のCSSファイルを配り、3つの指定クラスがどこかの画面に
   現れる」ことでしかない。指定クラスは「辿れる範囲のどこかに1回出ればよい」という
   ゆるい基準（`tests/inventory.py`の`_ui_classes`のdocstring参照）で、**画面ごとに
   同じ見た目になっているかは検査していない**。実際にレンダリングされた画面を
   目視・スクリーンショット比較した記録は、このレーン・指揮役側のどちらにも見当たらない

**どう直すか**: 「見た目が揃った」を「共通CSSを配布し、契約が求める3クラスの出現を
確認した」に narrow する。視覚的な一致（色・余白・配置）を主張するなら、スクリーン
ショット等で見る役（画面担当レーン）の結果を突き合わせてから言う。あわせて
`rulings.md`に「見た目は各スタックの流儀でよい」という既存裁定との関係を一言残す。

## 6. 判定器そのものの点検（指揮役からの依頼、11:50〜）— 契約の「合格の条件」が実装されていない検算が2つ

**指揮役の主張**: 「今日出た8件の判定器欠陥（型は`review/2026-09-06_指揮役の反省.md`追記3
参照）と同じ形が他に残っていないか見てほしい」という依頼。主張ではなく依頼だが、
「判定器はもう塞ぎきった」という暗黙の前提を検証する。

**示された根拠**: `tests/checks.py`・`tests/inventory.py` は全緑（`tests/compare.py`で確認済み）。

**根拠が届いていない範囲**: `spec/acceptance.md` は検算6・検算7それぞれに
**「どう確かめるか」の手順を3〜4段書いており、そのうち後半の手順（能動的に拒否されることを
確かめる）が「合格の条件」に明記されている**。実装されている`tests/checks.py`の
`_reserve`（検算6）と`_care`（検算7）は、**前半の受動的な手順しか実装していない**。

| 検算 | `acceptance.md`が定める合格条件 | `tests/checks.py`が実際に確認している範囲 |
| --- | --- | --- |
| 検算6（322-351行） | ①③④ 既存データに重なり0件／**重複するAPI新規作成が拒否され、
件数が変化しない**／**キャンセル済みの時間帯には新規作成できる** | `_reserve`は①のみ。
②③④は未実装。`POST /api/reservations`を一度も送らない |
| 検算7（355-378行） | 記録行の実施者が空でない／**実施者を指定しない作成APIが拒否され、
件数が変化しない** | `_care`は前半（既存記録の非空確認）のみ。**後半の拒否確認は未実装** |

つまり**契約書（acceptance.md）そのものが「これも確かめよ」と明記している範囲が、
判定器の実装から丸ごと抜けている。** 今日の8件（型5〜8＝判定器が契約より狭い前提を
置いた）と同じ形だが、今回は「狭い前提」というより**契約の後半部分を実装し忘れた**という
より単純な欠落。

**実測**（11:55、5実装すべてへ実際にAPIを叩いて確認。判定器を通さず直接検証）:

| 確認項目 | Go | Rails | Laravel | FastAPI | Next.js |
| --- | --- | --- | --- | --- | --- |
| 重複予約の新規作成 → 409で拒否 | OK | OK | OK | OK | OK |
| 実施者なしの記録作成 → 422で拒否 | OK | OK | OK | OK | OK |
| キャンセル済み時間帯への新規作成 → 成功 | OK | OK | OK | OK | OK |

**5実装とも現状は正しく動いている（今回作ったテスト用データは全て後始末済み）。**
今日の時点でのバグではない。**問題は「この動作を保証する自動検査が無い」こと。**
今後どれか1実装がリファクタで409/422を返し忘れても、`tests/run.py`は全緑のまま気づかない。

**もう1つ、`_reserve`単体の脆さ**: `GET /api/reservations`が空配列を返しても
（実装が壊れて0件しか返さない場合など）、`_reserve`は重なりを1件も見つけられず
「0件で重なり0」を**そのままOKとして返す**。件数の下限チェックが無く、
今日の反省でいう「対象0件でも緑になる」空振りパターンそのものが残っている
（他の検算——検算3・4・5・7・8・在庫系——は軒並み最低件数のガードを持つが、検算6だけ持たない）。

**どう直すか**:
1. `tests/checks.py`の検算6に、`acceptance.md`の手順3・4を実装する:
   既存の重なりへ`POST /api/reservations`を実際に送り409＋件数不変を確認する一件、
   キャンセル済み時間帯への新規作成が成功することを確認する一件
2. 検算7に、`performed_by_staff_id`を欠いた`POST .../care-records`が422＋件数不変で
   拒否されることを確認する一件を足す
3. `_reserve`に他の検算と同じ最低件数ガード（例: `if not rows: return False`）を足す
4. 今回のように**契約書の「どう確かめるか」に書いてある手順を、実装した検査と1行ずつ
   突き合わせる**作業を、検算9項目すべてでやり直す（今回は6・7しか見ていない）

## まとめ

いちばん重い指摘は1番（FastAPIの `POST /api/reservations` 500）。
「全通過・食い違い0」という一番強い主張の直下に、**検査の対象外にある実際の500エラー**
が現存している。しかもこれは指揮役以外（レーンR）が今日の朝にすでに報告済みの穴であり、
「読まれずに完了と判断した」という今日すでに起きた事故1件目・3件目と同じ形をしている。

2番・3番は同じ根っこ（papers関連3件の「確かめられない」の扱い）を持つ。「確かめられ
ない」を「無い」に落とすと嘘になるのと同様に、**「在る」に格上げしても嘘になる**。
4番はこのレーンで唯一「主張どおり」と確認できたもの。

5番は主張の範囲が定義されておらず、既存の裁定（見た目はスタックごとでよい）との関係が
書かれていない。

6番（判定器そのものの点検）が今回いちばん重い。**契約書(`acceptance.md`)が自分で
「これも確かめよ」と書いている手順の後半が、判定器に実装されていなかった。**
今日は5実装とも実際の挙動は正しかったので実害は無いが、**この2つの検算は
今後の回帰を検出できない状態のまま「全緑」と報告され続ける。** 「今日出た8件と同じ型が
残っていないか」という問いへの答えは「ある。ただし今日の8件とは違い、実装忘れ型」。
