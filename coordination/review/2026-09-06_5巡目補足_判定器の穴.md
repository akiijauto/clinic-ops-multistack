## まず良い知らせ：5-01（飼主氏名）は既に手当てされかけている

`tests/inventory.py` に `_same_data`（「データ 実装が読んでいる中身が data/ と一致する」）という
検査が**既に追加されている**（コメントに「読むだけの役が見つけた」と明記あり＝私の報告を受けたもの）。
これは正しい方向の修正で、**文字列を初めて `data/seed.json` と照合する**検査になっている。

### ただし、この新しい検査自体に既存フィールド名との食い違いがある（実測）

```python
for o in (seed.get("owners") or [])[:6]:
    for fld in ("name_kanji", "name_kana", "address1", "tel"):   # ← "tel"
        ...
for p in (seed.get("patients") or [])[:6]:
    for fld in ("name", "species", "breed"):                      # ← "name"
        ...
```

**実際の `data/seed.json` のキー名を確認すると**（`python3` で直接読み出し、API応答でも確認）:
```
owners:   id, owner_no, name_kana, name_kanji, postal_code, address1, address2, phone, mobile, deleted_at
patients: id, karte_no, owner_id, name_kana, name_kanji, species, breed, sex, birth_date, neuter_date, deleted_at
```
`tel` というキーは存在しない（正しくは `phone`）。`patients` に `name` というキーは存在しない
（正しくは `name_kanji`）。`o.get(fld)` / `p.get(fld)` は存在しないキーに対して例外を出さず
静かに `None`（偽）を返すため、**この2フィールドはチェック対象リストに1件も追加されない**
（例外も出ずテストは「動いている」ように見える。しきい値`8件`は他のフィールドだけで超えるので
「検査が働いていない」の自己防御にも掛からない）。

**なぜ問題か**: 結果として、この新しい検査は
- 飼主の**電話番号**の食い違いを一度も見ない
- **動物（Patient）の氏名（`name_kanji`）の食い違いを一度も見ない**——まさに今回見つかった
  「氏名だけがずれる」型の欠陥を、**患者側では今も検出できない**構造になっている
  （飼主側の `name_kanji` は正しいキー名なので検出できる。非対称）

指揮役へ: `("name", "species", "breed")` → `("name_kanji", "species", "breed")`、
`"tel"` → `"phone"` に直すだけで直ると見られる（実装ではなく検査側の1行修正）。

## 新たに見つけた「検算・在庫検査が値そのものを見ていない」箇所

### BS-1. 検算5（検査の判定）は、画面の `data-check-flag`（色）を一度も見ていない【重い】

`spec/screens.md` #10 は「**判定の文字と色（`data-check-flag`）は独立に確認する——片方だけ出す
実装は不合格**」と名指しで要求している。しかし `tests/checks.py` の `_lab_flag`（検算5）は
`GET /api/lab-tests/{id}` という**JSON APIのみ**を叩き、`judgment` 文字列だけを比較している。
`data-check-flag` という文字列は `checks.py` 全体を検索しても1件も出てこない
（`grep -n "data-check-flag" tests/*.py` → 0件）。

**なぜ問題か**: ある実装がAPIでは正しい`judgment`を返しつつ、検査画面のHTMLに
`data-check-flag`（色分けの根拠）を一度も出さなくても、検算5は永遠に緑のまま。
契約が名指しで求める「独立に確認する」という要求を、判定器自身が満たしていない。

### BS-2. 「在庫」の画面・APIルート検査は常にGETしか送らず、405を「在る」に数える【重い・構造的】

`tests/inventory.py` の `_probe()`（画面・APIルート双方が使う共通関数）は
```python
status, _, _ = c.get(real)
...
if status < 400 or status in (401, 403, 405):
    present.append(p)
```
と**必ずGETのみ**で呼び出し、**405（メソッド不許可）を「在る」の側に数える**。
これはPOST専用エンドポイントに対してGETを送れば当然405が返る、という前提の実装だが、
**結果として「そのルートに実際にPOST/PATCH/DELETEを送ったら動くか」は一度も確認されない。**

書き込み経路を実際に叩くのは、新設された `_write_roundtrip`
（`POST /api/reservations` →確認→ `cancel`）**1本だけ**。ほかの書き込み系エンドポイント
（会計伝票の明細追加・確定、書類の取込、投薬・予防の保存、スタッフ選択、入院の退院処理、
DM CSVの実際の内容 等）は、在庫検査・検算のどちらからも**一度もPOST/PATCH/DELETEされない**。

**なぜ問題か**: 例えば「会計伝票のPATCHがGoで受け取った明細を無視してサイレント無反応」
「FastAPI/Next.jsのPATCHが405で未実装」（5巡目本編で報告済み）は、`_probe`が
GETしか送らずかつ405を合格扱いにする限り、**inventory検査にも検算にも一度も引っかからない
構造**になっている。`_write_roundtrip`と同じ往復確認を他の書き込み経路にも広げない限り、
この種の欠陥は今後も"全部緑"の報告をすり抜け続ける。

### BS-3. 検算8（死んだリンク）は「26画面中10画面辿れれば合格」であり、全画面到達を求めていない【重い・team-lead依頼に直結】

```python
if len(seen) < 10:
    return False, f"{len(seen)} 画面しか辿れなかった（26画面あるはず）"
return True, f"{len(seen)} 画面を辿って切れなし"
```
しきい値は**10画面**。5巡目本編で報告した「Next.jsは深さ2クロールで38パスしか辿れない」
「Railsのナビに`/dm`・`/sales`が無い」は、いずれも**10を大きく超えて**いるため、
この検査はどちらも緑のまま通す。**契約の26画面のうち、どの画面が辿れないかを
名指しで検出する仕組みが存在しない。**

### BS-4. 検算4（画面と印刷の一致）は4つの数値（体温・脈拍・呼吸・体重）だけで、文章項目は一度も比較しない【中】

`spec/screens.md` #9 は「印刷しても同じ内容が出ることが前提」とカルテ全体について書いているが、
`_screen_vs_print` が比較するキーは
```python
keys = ["progress_note.temperature_c", "progress_note.pulse",
        "progress_note.respiration", "progress_note.body_weight_kg"]
```
の4つのみ。**主訴・症状・診断・治療（`Visit`の文章項目）・経過記録の「経過」「処置」「メモ」欄は
一度も画面と印刷で突き合わせていない。** これらには`data-check`キー自体が定義されていない
（`spec/screens.md`の目印表を参照）ため、**契約上そもそも機械では確認できない設計**になっている
——検査の不備というより、契約側の目印不足に近い。参考として記録する。

サンプル数も「先頭6患者」（`FIX.seed["patients"][:6]`）に限られる。

### BS-5. 検算1・検算2は集計の総額／単一の代表伝票だけを見ており、内訳の各行（担当名・分類名）は一度も照合しない【中〜重い】

検算1は`by_category`/`by_staff`/`by_date`の**合計**が一致するかだけを見る。各行の
「どの担当・どの分類にいくら付いているか」という**内訳そのものの正しさ**（例：担当Aの売上が
実は担当Bのものとして計上されている、といった按分違い）は、**総額さえ合っていれば検出されない**。
検算2も`FIX.seed["billings"]`のうち条件に合う**最初の1件**、`billings[0]`しか見ない。

**この型は今回の氏名バグと同じ構造**（総額・件数という「数字」だけを見るせいで、
中身の対応関係がずれていても緑になる）。今回は氏名で顕在化したが、**同種の内訳齟齬が
金額でも起こり得ることを示す一般的な弱点**として記録する。

### BS-6. 検算7（入院記録の実施者）は画面の `data-check="care_record.performed_by"` を一度も見ない【中】

`spec/screens.md`の目印表に`care_record.performed_by`（入院の記録行の実施者名、空にしない）
が明記されているが、`_care`（検算7）が叩くのは`GET /api/hospitalizations/{id}/care-records`
のみで、**入院画面のHTML自体は一度も取得しない。** APIが正しい`performed_by_staff_id`を
返していても、画面がその名前を`data-check`付きで実際に描画しているかは未検証のまま。

### BS-7. `_marks`（data-testid在庫検査）は`screen-*`接頭辞の目印しか必須にしない【重い・5巡目本編の複数事象の根本原因】

```python
miss = [i for i in miss if i.startswith("screen-")]
```
行単位・空表示の目印（`row-visit` `row-reservation` `empty-papers` 等）は**意図的に対象外**
にされている（理由はコメントにある通り「データ次第で出ないことが正しい場合がある」）。
これは合理的な設計判断だが、**結果として5巡目本編で報告した以下の事象は、
この検査からは原理的に見えない**：

- FastAPIが`row-visit`等を`data-testid`ではなく`data-check`として出力（属性の取り違え）
- Laravelが`row-visit`を経過記録の`<tr>`に誤って付与
- Next.jsのカルテで`row-visit`が6件中1件しか出ない

いずれも「画面レベルの目印はある（`screen-karte`は出ている）が、行レベルの目印がおかしい」
という型で、**「目印はあるが中身が無い」の逆——目印の名乗り自体が壊れている**状態。
検査の設計判断（データ依存の目印は必須にしない）自体は妥当だが、**「screen-*さえ在ればよい」
という線引きが、行レベルの構造的な誤りを見えなくしている**点は指揮役へ申し送る価値がある。
