# 指揮役の判断ミス — 「テストが緑」を「完了」と読んだ

**2026-09-06、オーナーの指摘で発覚。** 指揮役（統括）である私の誤りである。

## 何をしたか

1. 5実装で共通テスト14件が全部OK・食い違い0になったのを見た
2. **それをもって「完了」と判断**し、公開ゲートを通してコミット・push した
3. コミットメッセージに「**残りの画面とAPIを配線し**」と書いた
4. オーナーへ「戻り3件は全部直っています」と報告した

## 実際は

**レーンDの報告に、はっきりこう書いてあった。**

> **未完了。** 残り23画面・26 APIの実装を続ける。優先順位は指揮役の指示があれば従うが、

レーンA・B・C・Eの報告にも未実装・未配線の記述が残っていた。
**私はこれらを読まずに完了と判断した。**

## 原因は3つある。どれも指揮役の側にある

### 1. 完了の条件を、測れるものに縛っていなかった

各レーンへ出した再開の指示は「**残っている画面とAPIの配線を続けてください**」だった。
**どこまでやったら終わりかを書いていない。** 書いてあったのは
「``python tests/run.py`` で14件OKを確認」だけで、これは**戻りが無いことの確認**であって
**作り終えたことの確認ではない**。

指揮役が終わりを定義しなければ、緑になった時点が終わりに見える。

### 2. 判定器に、画面の存在を見る検査が無い

レーンRが正しく指摘している。

> 共通テスト（``tests/run.py``）が緑でも、この6画面の不在は検出されません。
> 検算8のクローラーは「辿り着けたリンクが生きているか」だけを見ており、
> 「26画面すべてが存在するか」までは見ていない穴があります

**リンクが張られていない画面は、クローラーには最初から存在しない。**
だから「死にリンク0」と「画面が揃っている」は別のことなのに、私は前者で後者を代用した。

なおレーンCだけは自力でこの穴を埋めていた
（``openapi.yaml`` の画面ルート41件を ``route:list`` と突き合わせ、欠落0件）。
**同じことを全レーンに課すのが指揮役の仕事だった。**

### 3. 自分で書いた教訓を、自分で破った

同じリポジトリの ``実績-2026-09-06.md`` に、私はこう書いている。

> **「検算が緑」と「検算が働いている」は別のこと。**

今回はその一段外側 — **「検算が緑」と「作り終えた」は別のこと** — で同じ間違いをした。
教訓を書くことと、次の判断で使うことは別である。

## 改善（この企画で実際に入れるもの）

| # | 対策 | なぜ効くか |
| --- | --- | --- |
| 1 | **画面の在庫検査を判定器に足す。** ``spec/openapi.yaml`` の画面ルート全件を列挙し、各実装で200が返るかを1件ずつ確かめる | クローラーの穴（リンクが無い画面は見えない）を塞ぐ。レーンCが単独でやっていたことを共通化する |
| 2 | **完了の定義を数で書いて渡す。** 「画面41ルートすべてが200」「未実装APIが0件」を各レーンの完了条件にする | 「配線を続けてください」では終わりが決まらない |
| 3 | **待機に入る前の自己点検を義務にする。** 何が残っているかを ``status/lane-*.md`` の決まった見出しに書かせる | 今回はオーナーが指示して初めて出てきた。指揮役が最初から求めるべきだった |
| 4 | **指揮役は、緑を見たら報告を読む。** テスト結果だけで完了と判断しない | 今回、答えは全部 ``status/`` にあった。読んでいない |

## いちばん短い言い方

**緑は「壊れていない」の証明であって、「出来ている」の証明ではない。**
出来ているかは、作るものを数えて、数えたものが在ることを確かめないと分からない。

# 追記 — 判定器の欠陥4件目は、指揮役が作った（同日）

上の反省を書いた**直後に、同じ型の間違いをもう1つ出した。**

## 何をしたか

穴を塞ぐために在庫検査（`tests/inventory.py`）を書いた。そのとき、パス変数に入れる値を
**実データを見ずに直に書いた。**

```python
_SAMPLE = {"karte_no": "10002", "visit_id": "1", "owner_no": "1", "kind_id": "1", ...}
```

## 実際のデータ

| 書いた値 | `data/seed.json` の実際 |
| --- | --- |
| `owner_no = "1"` | `"O-00001"` 形式の表示用番号 |
| `visit_id = "1"` | その診察は **patient_id 18** のもの。karte_no 10002 の診察ではない |
| `kind_id = "1"`（vaccine_core） | 投薬40件は**すべて heartworm**。vaccine_core は1件も無い |
| `paper_id = "1"` | `papers` というキーが seed に**存在しない**（動的作成のみ） |

つまり **実装があるのに404** を返し、それを「未実装」と報告していた。

## 誰が見つけたか

**レーンA（Go）が1件ずつ実測して見つけた**（`qa/lane-a.md` Q-A-15）。
指揮役の指示を鵜呑みにせず、「10件が欠けている」という前提そのものを疑った。

## 被害

誤った数字で5レーンに指示を出した。とくに**レーンCには濡れ衣を着せた。**

> 「あなたは欠落0件と報告したが、実測では画面5件・API31件が404だ」

**レーンCの元の報告が正しく、実測では欠け0件だった。** 指摘した側が間違っていた。

| 実装 | 誤（固定値） | 正（data/ から引いた値） |
| --- | --- | --- |
| Go | 画面4・API6 | **画面2・API2** |
| Rails | 画面8・API12 | **画面4・API7** |
| Laravel | 画面5・**API31** | **欠け0** |
| Next.js | 画面14・API11 | **画面2・API2** |
| FastAPI | 画面30・API28 | **画面20・API24** |

## 直した内容

1. **値を `data/` から引く。直に書かない**
2. **`visit_id` はその診察の患者の `karte_no` と対で選ぶ。** 別々に選ぶと正しく404になり、欠けと誤認する
3. `key` の語彙は実装が出している一覧ページから拾う
4. **「無い」と「確かめられない」を分けた。** Paper は seed に1件も無いので、
   起動直後に存在しないのが正しい。これを欠けと数えるのは嘘になる
5. ただし**「確かめられない」を逃げ道にできないよう**、25%を超えたら検査自体を失敗させる

## 教訓（上の反省に足りていなかったもの）

上では「緑は出来ている証明ではない」と書いた。**それだけでは足りなかった。**

> **赤も、出来ていない証明ではない。**
> 判定器が間違っていれば、実装があっても赤になる。
> 判定器の欠陥は4件とも「特定の実装だけが落ちる」形で現れた。
> **1件目〜3件目はレーンが見つけ、4件目は指揮役が作った。**

そして、**実データを見ずに書いた固定値は、実装ではなく判定器を間違わせる。**
期待値を `data/` から独立に計算するという原則は最初から立てていたのに、
在庫検査を足すときにその原則を適用しなかった。

# 追記2 — 訂正のほうが誤りだった（同日・3件目）

追記1で「レーンCに濡れ衣を着せた」と書いた。**その訂正自体が誤りだった。**

## 何が起きたか

1. 09時台、欠陥のある在庫検査で測り、**Laravel は API 31件が404**と出た
2. レーンCへ「あなたは欠落0件と報告したが、実測では31件が404だ」と伝えた
3. レーンCが**1時間かけて31件を実装した**
4. 10時台、判定器を直して測り直したら **Laravel は欠け0** だった
5. これを見て「最初から出来ていた。私の指摘が誤りだった」と結論し、**本人に謝った**

**4の数字は、3の作業が終わった後のものだった。** 作業後の数字を、作業前の数字と比べた。

## gitで確かめた事実

| 時点 | `stacks/laravel/app/Http/Controllers/Api/` |
| --- | --- |
| コミット 46722e3（作業前） | **5ファイル** |
| いま（未追跡の新規追加） | **+14ファイル**、`routes/api.php` に83行追加 |

**API 31件は本当に未配線で、レーンCが作った。** 私は他人の成果を「最初から在ったもの」と読み違え、
やっていない失敗を謝った。**褒めるべきところで謝るのは、評価として逆方向に間違っている。**

なお画面5件のほうは判定器の欠陥で正しい（レーンCの言い分どおり）。
**1つの指摘の中に、正しい部分と誤った部分が混在していた。** それを分けずに全部撤回した。

## 原因

**測った時刻を確かめずに、2つの数字を比べた。**

並列体制では、担当が動いている最中に指揮役が測ると、**数字は指揮役の知らないうちに変わる**。
測定値には「いつ測ったか」が必ず付いていなければ、比較は意味を持たない。

## 対策

1. **測ったら時刻を残す。** 比較するときは、両方の時刻と、その間に何が起きたかを確かめる
2. **撤回するときは、指摘を項目ごとに分ける。** まとめて撤回しない。
   今回は「画面5件＝私の誤り」「API31件＝正しい指摘」で、扱いが逆だった
3. **判断を変える前に、変化の原因を1つ挙げる。** 「直ったから0になった」のか
   「最初から0だった」のかは、gitを見れば数秒で分かった。見なかった

# 追記3 — 判定器の欠陥はこの日だけで8件。うち7件を指揮役が作った

「緑をすり抜けるもの」を塞ぐたびに、**塞いだ側に新しい間違いが入った。**

| # | 判定器の欠陥 | どう見えたか | 見つけたのは |
| --- | --- | --- | --- |
| 1 | 正規表現が普通のHTML文書を読めない | 全実装で目印が0件 | レーンA |
| 2 | HTTPヘッダを大文字小文字で区別 | FastAPIだけ1画面しか辿れない | レーンD |
| 3 | 絶対URLを辿らない | Laravelだけ1画面しか辿れない | レーンC |
| 4 | **画面の不在を検出できない** | 全実装が緑のまま未実装が残る | レーンR |
| 5 | **実データを見ずに固定値を書いた** | 実装があるのに404と報告 | レーンA |
| 6 | **「404でなければ在る」で500・406を通した** | 壊れていても緑 | レーンB |
| 7 | **契約と違う型で叩いた**（kind_id に文字列） | 契約を守った実装だけが落ちる | レーンD |
| 8 | **鍵の文字クラスを狭く決めた**（`.` を除外） | 別々の鍵が同じものに見え、「1個しか無い」と誤報 | レーンC |

さらに、**契約が404を認めている経路に記録の無い相手を選んで投げた**（レーンD）、
**語彙の出どころを3回決めつけて3回とも外した**（`key=reception` / 一覧ページ /
`masters.json` のキー名）も同じ型である。

## 共通する形

**5〜8はすべて「判定器が、契約や実データより狭い前提を置いた」ことが原因である。**

    判定器が読み取れる範囲を狭く決めると、**正しく作ってあるものが「無い」ことにされる。**

そして**その誤りは、必ず「特定の実装だけが落ちる」形で現れる**。
実装の質の差に見えるが、中身は判定器の間違いである。

## 見分け方（この日で確立したもの）

| 現れ方 | まず疑うもの |
| --- | --- |
| 1つの実装だけが**たくさん**落ちる | **判定器** |
| 落ちる実装が分かれ、検査が1件ずつ | 実装 |
| **契約を素直に読んだ実装だけ**が落ちる | **判定器**（多数決を根拠にしない） |
| 全実装が緑なのに、契約の要求が実装されていない | **検査が無い** |

## いちばん高くついた教訓

**多数決を根拠にするな。**
「5実装のうち4つが通っている」は、その4つが正しい証明ではない。
判定器が間違っていれば、**間違いに合わせた実装のほうが通る**。
この日、その誤りで2回、契約を守った実装を「壊れている」と断じた。

## 測定の信頼性について（レーンCの報告より）

`php artisan serve` は単一スレッドで動くため、判定器が連続で多数の要求を投げると
**一過性の404を返すことがある**（同じ要求を直後に叩くと200）。

    **測定の失敗と、実装の失敗は別である。**
    赤が出たら、まず「もう一度測る」。再現しなければ測定側を疑う。
