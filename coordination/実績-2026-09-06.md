## 見積もりとの差

計画では **1スタックあたり 20,000〜25,000行** と見ていた。**2026-09-05時点は 2,300〜4,700行**。

**大きく外した。** 理由ははっきりしている。

**26画面すべてを作り込んでいない。** いまの状態は「**共通テスト14件が通る範囲**」であり、
各レーンの報告にあるとおり、**保存・登録・編集のフォームは繋いでいない**。
画面の多くは参照専用のスタブである。

- レーンB「これらはまだ『検算8を通す最小限』の実装です」
- レーンE「実際に配線したのは参照系のみ。登録・編集系のフォームはまだ繋いでいない」

つまり **17,024行は「26画面を作り切った量」ではなく「検算が通る量」** である。
見積もりの 20,000〜25,000行 は前者を指していたので、比べる対象が違う。

**この差を「見積もりが良かった/悪かった」と読まないこと。** 作ったものが違う。

### 2026-09-06 追記——行数は伸びたが、なお見積もりの半分以下

上記の実測後、5レーンが並列で残りの画面・APIを配線し、**行数は7,100〜12,100行まで
伸びた**（前節）。契約が定義する画面ルート42件・APIルート36件（計78件）のうち
75件が、5実装すべてでGETによる存在確認まで完了している。

それでも**計画の20,000〜25,000行には届いていない**（最大のGoで12,066行、
見積もりの半分強）。この差の一部は、行数の測り方の違いでは説明できない
——これは書いたコードの絶対量の話であり、対象範囲は当初の想定（26画面ぶんの
保存・登録・編集まで含む）に近づいたはずである。**なぜまだ半分以下なのか
（言語・フレームワークごとの生産性の違いか、機能の実装密度がまだ薄いのか）は
このレーンでは切り分けていない。未確認として残す。**

さらに重要な留保がある。GETで「在る」ことが確認できたのと、**書き込み
（POST/PUT/DELETE）が正しく動くことは別**である。共通テストは書き込みを
一度も検査しない。実際に本レーンがPOSTを送って確かめたところ、
FastAPIの予約作成APIは契約どおりの入力（タイムゾーン付き日時）で
500エラーを返す（README「読む側（監査）で見つかった穴」を参照、
2026-09-06 11:49実測）。**「行数が伸びた」＝「26画面が正しく動く」ではない。**

## 何が言えるか（実測に基づくもの）

| 言えること | 根拠 |
| --- | --- |
| 同じ契約に対して**5つの実装が同じ判定を返した**（GETで確かめられる範囲） | `tests/compare.py` の実行結果、2026-09-06実測。22件×5実装すべて OK、食い違い0 |
| 税抜売上が**5実装とも 5,185,704円**で一致 | 判定側が `data/` から独立に計算した期待値と一致 |
| 契約の画面・APIルート78件のうち**75件が5実装すべてに存在する**（GET確認） | `tests/inventory.py`、2026-09-06実測 |
| 5レーン並列＋統括1人で**1日のうちにここまで到達** | git のコミット時刻 |

## 何が言えないか

- **「26画面を5スタックで作り切った」とは言えない。** 参照系の存在はGETで確認できたが、
  **書き込み（保存・登録・編集）が正しく動くとは限らない**——FastAPIの予約作成APIは
  契約どおりの入力で500を返す（2026-09-06 11:49実測、READMEを参照）。共通テストは
  書き込みを検査しないため、この種の欠陥が他にも残っている可能性は**未確認**
- **「通常なら何日」とは言えない。** 手元に他者の実測が無い
- **応答時間の比較はできない。** `/healthz` を1回叩いただけで、
  起動直後かどうか・サーバの形（開発用か本番相当か）が揃っていない
- **「40/42画面・35/36API」を「在る」の確定値として扱えない。** 残り3件
  （書類=紙カルテPDFの個別参照・削除）は、データが無く自動検査が判定を保留している
  だけでなく、**手動で叩いた結果が測るたびに変わる**（同日11:41と11:49で、
  どの実装が200を返すかの組み合わせが変わった）。存在の有無がサーバーの
  起動来歴に依存し再現しないため、「確かめられない」以上のことは言えない

## この企画で本当に得られたもの

行数でも速さでもない。**「同じであることをどう確かめるか」の作り方**である。

判定側の欠陥が**3件**出た。3件とも「**特定の実装だけが落ちる**」形で現れ、
実装の質の差に見えて、中身は判定器の間違いだった。

| # | 判定器の欠陥 | どう見えたか |
| --- | --- | --- |
| 1 | 正規表現が普通のHTML文書を読めない | 全実装で目印が0件 |
| 2 | HTTPヘッダを大文字小文字で区別 | **FastAPI だけ**1画面しか辿れない |
| 3 | 絶対URLを辿らない | **Laravel だけ**1画面しか辿れない |

さらに、**検算そのものが検算になっていない**箇所も見つかった
（消費税の丸めの規則が、150枚すべての伝票でどちらの実装でも緑になる）。

> **「検算が緑」と「検算が働いている」は別のこと。**
> **「あの実装だけ通らない」を見たら、まず判定側を疑う。**

## 2026-09-06 追記——今日いちばんの学び

2026-09-05までの学びは「判定器（判定する側）は間違える」だった。2026-09-06は、
その一段上——**「緑をどう読むか」を統括役自身が間違えた**日になった。
詳細は `coordination/review/2026-09-06_指揮役の反省.md` と `coordination/qa/rulings.md`
に書いてある。ここでは要約しすぎず、骨子をそのまま残す。

### 緑は「壊れていない」の証明であって、「出来ている」の証明ではない

共通テスト14件が5実装とも緑・食い違い0になったのを見て、統括役は「完了」と判断し、
公開ゲートを通してコミット・pushした。実際にはレーンの報告に「未完了。残り23画面・26 API」
とはっきり書いてあった。**読まずに緑だけで判断した。**この日、共通テストは22件まで
増えて全実装が通過し続けているが、README「読む側で見つかった穴」に書いたとおり、
**その22件はPOST/PUT/DELETEを一度も送らない**。書き込み経路の欠陥（FastAPIの
予約作成APIが500を返す）は、2026-09-06 11:49時点で本レーンが再現しても直っていない。
**「今日も緑」を「今日も出来ている」に読み替えないこと。**

### 赤も「出来ていない」の証明ではない

判定器が間違っていれば、契約を守った実装ほど落ちる。実際に起きた例：
FastAPIが契約どおり `kind_id` を整数として受け取り、判定器が文字列を渡していたために
422を返した場面で、統括役は「4実装が通っているのだから、あなたが直せ」と2度伝えた。
FastAPIレーンが反論しなければ、契約を守った実装のほうが「壊れている」ことにされていた。

### 判定器の欠陥は今日までで6件。3件は統括役自身が作ったと本人が明記している

1〜3件目（正規表現がHTML文書を読めない・HTTPヘッダの大文字小文字・絶対URLを辿らない）は
各レーンが見つけた。4〜6件目（実データを見ずに固定値を書いた・500を「在る」に数えた・
`data-testid` を確かめる検査が無かった）は、統括役が在庫検査を書く過程で自分が作ったと
`指揮役の反省.md` に明記している。**「1〜3件目は誰が作ったか」はこのレーンでは未確認**
（`rulings.md` に記載が無い）。

### 統括役の判断ミスは複数回記録されている。少なくとも4件は他者の指摘で発覚した

`qa/rulings.md` `review/2026-09-06_指揮役の反省.md` に記録されている判断ミスのうち、
**発覚のきっかけが明記されているもの**は次の4件——（1）「テストが緑」を「完了」と
読んだ（オーナーが指摘）、（2）実データを見ずに判定器へ固定値を書いた（レーンAが指摘）、
（3）作業後の数字を作業前と比べ、他人の成果を「最初から在った」と読み違えた
（レーンCの報告から発覚）、（4）判定器が契約と違う型で叩いていたのに実装側へ
「直せ」と指示した（レーンDの反論から発覚）。もう1件（在庫検査が500番エラーを
「在る」の側に数えていた）は、レーンAの別件の報告への対応中に統括役が書き記したもので、
**「誰が最初に気づいたか」までは記録上判然としない（未確認）。**
はっきり言えるのは、**指揮役自身が最初に気づいた例が記録に見当たらないこと。**

### 多数決を根拠にした判断が2件、どちらも誤りだった

「5つのうち4つが通っている」ことは、その4つが正しいことの証明ではない。
判定器が間違っていれば、間違いに合わせた実装のほうが通る。上記の`kind_id`型の件と、
Laravelの欠落APIを巡る「4対1」の場面（当初は数字を測った時刻を確かめずに比較し、
レーンCの成果を「最初から在ったもの」と読み違えた）の2件で、統括役はこの誤りを犯した。

### いちばん短い言い方

**緑は「壊れていない」の証明であって、「出来ている」の証明ではない。
赤も「出来ていない」の証明ではない。** 出来ているかどうかは、作るものを数えて、
数えたものが実際に——GETだけでなく書き込みも含めて——動くことを確かめないと分からない。

## 応答時間の実測（2026-09-06 19:35）

**以前は「応答時間の比較はできない」と書いた。** `/healthz` を1回叩いただけで、
起動直後かどうか・サーバの形が揃っていなかったからである。
判定器が Laravel に対してだけ極端に遅いことに気づいて測り直した。

| 実装 | `/healthz` | `/today` | `/sales` |
| --- | ---: | ---: | ---: |
| Go | **1.1ms** | 1.2ms | 1.8ms |
| FastAPI | 1.8ms | 5.0ms | 42ms |
| Next.js | 11ms | 9.0ms | 12ms |
| Rails | 33ms | 71ms | 219ms |
| **Laravel** | **246ms** | 249ms | **464ms** |

判定器（在庫検査）の所要時間は **Go 6秒に対し Laravel 240秒**。**40倍**である。

### この数字が言っていること・言っていないこと

**言えること**

- `/healthz` は何も計算しない。**それが246msかかるのは、要求ごとの起動処理の重さ**である
- **開発用サーバで比べるかぎり、この差は実在する。** 検査が時間切れになるほどに

**言えないこと**

- **言語の速さの比較ではない。** `php artisan serve` は毎回フレームワークを起動し直す。
  本番構成（opcache + FPM や、Go以外でも常駐プロセス）では桁が変わる
- **アプリの作りの良し悪しでもない。** `/sales` の差（Go 1.8ms / Laravel 464ms）には
  集計処理も含まれるが、`/healthz` の差がそのまま乗っているだけとも読める

    **測った条件を書かない数字は、速さの主張には使えない。**
    ここに書いたのは「**この企画の開発環境では、こう見えた**」というだけである。

### 実務上の意味

**判定器が同じ検査を全実装に当てる以上、いちばん遅い実装が全体の待ち時間を決める。**
5実装ぶんを順に回すと、Laravel だけで4分かかる。
並列で走らせるか、Laravel 側を常駐構成にするかを、必要になったら考える。
