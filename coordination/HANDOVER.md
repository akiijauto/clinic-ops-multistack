# トークンの使い方についての反省と対策

オーナーからの指摘（2026-09-05）:

> skillを作成して実行させてトークン効率を最大にするなどの工夫が必要ではないか

**そのとおりである。** いまの作りは無駄が大きい。原因と対策を書く。

## いちばん大きな無駄：契約の読み直し

`spec/` は合計 **約193KB**（README 4.6K / model 8.5K / screens 41.6K /
acceptance 30.8K / openapi 108.4K）。

**レーンは起動のたびにこれを読む。** 制限で止まって再開するたびに読み直す。

6レーン × 193KB = **1回の再起動で1.16MB**。制限で何度も止まる前提だと、
**実装そのものより読み直しのほうが高くつく**。

## 対策1：レーンが読む量を減らす（効果が最も大きい）

**openapi.yaml 108KB を丸ごと読ませない。**

- 領域ごとに分割する（受付・診療・会計・入院予約・設定）
- レーンは**自分がいま作っている領域の分だけ**読む
- 全体像は `spec/README.md`（4.6KB）で足りる

同じことを `screens.md`（41KB）にも行う。

**見込み**: 1レーンあたり 193KB → 40KB 前後。**約5分の1**。

## 対策2：skill にする

繰り返し貼る指示（起動文面・契約の読み方・完了条件）を skill にまとめ、
`/lane-a` のような短い呼び出しで済むようにする。

いまは起動のたびに `briefs/lane-*.md` を読ませているが、
**skill なら必要な部分だけが読み込まれる**。

置き場所は `.claude/skills/`。中身は各レーンの役割・所有ディレクトリ・
完了条件・質問の経路だけにし、**契約そのものは含めない**（契約は都度参照する）。

## 対策3：同時に走らせる数を減らす

**これは効率ではなく、成果の形の問題である。**

枠が有限なので、16並列にしても**総量は増えない**。増えるのは消費の速さだけ。

| 並列数 | 1つの枠で起きること |
| --- | --- |
| 16 | 16個が少しずつ進み、**全部が中途半端**なところで止まる |
| 2〜3 | 2〜3個が**区切りまで進む**。止まっても続きから再開しやすい |

**中途半端なところで止まると、再開時に「どこまでやったか」を思い出す費用がかかる。**
これも読み直しと同じ無駄である。

**勧め: 同時に動かすのは2〜3レーン。** 1レーンが1領域を終えたら次へ渡す。

## 対策4：レーンに「続きから」を書かせる

`coordination/status/lane-*.md` に、**次に何をするかを1行で**書かせる。
再開したレーンはそれを読めば、契約を全部読み直さなくても再開できる。

いまは進捗を書く決まりにしているが、**「次の一手」を書く決まりにしていない**。

## 対策5：題材側と枠を取り合わない

vet-karte 側が8並列で動いている。**同じ枠を食い合っている。**

どちらを先に通すかを決める。並行させるなら、**合計で2〜3並列**に収める。

## やらないほうがよいこと

- **モデルを下げて節約する** — レビュー層（レーンR）の質が落ちると、
  今日見つけたような不整合（`CareRecord` の項目名・`data-testid` の残存）が
  そのまま実装へ流れる。**直す費用のほうが高い**
- **検算を減らす** — 検算が減ると偽の緑が増える。今日すでに
  「何も動いていないのに緑になる検査」が2件見つかっている
