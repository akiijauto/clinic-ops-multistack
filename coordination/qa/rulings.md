# 指揮役の裁定（契約に関するもの）

**ここに書いたことは決定済み。** レーンは蒸し返さず、これに従うこと。
契約の文書（`spec/`）と食い違いを見つけたら、**この文書が正**として指揮役へ報告する。

## 2026-09-05 契約の凍結にあたって

`spec/acceptance.md` の作成者から6件の判断が報告された。**すべて採用する。**
理由を添えて記録しておく（後から「なぜこう決めたか」を追えるようにするため）。

| # | 論点 | 裁定 | 理由 |
| --- | --- | --- | --- |
| 1 | 売上の「担当」軸 | **`Billing.staff_id`（診療担当）**を使う。`cashier_staff_id`（会計担当）は使わない | 業務上「誰が売上を立てたか」は診療した人。会計を打った人ではない |
| 2 | 売上の「分類」軸 | 料金の2階層のうち**上位1階層のみ** | 階層の深さは比較の題材にならない（`model.md` で4階層→2階層に減らした判断と同じ筋） |
| 3 | **消費税の扱い** | **伝票単位で1回だけ切り捨て。** 分類別・担当別の内訳には消費税を含めず、**税抜で3方向一致**を取る | 内訳へ税を按分すると、**按分の方法しだいで答えが変わり、検算にならない**。税抜なら按分が要らず、5実装で必ず一致する |
| 4 | **HTMLの目印** | **両方残す。役割で分ける**（下記） | 一度「`data-check` に統一」と裁定したが、**それも撤回した。2つは別の仕事をしている** |
| 5 | 入院の実施者 | フィールド名は **`performed_by_staff_id`** | `model.md` に記載が無かった。確定して `model.md` へ反映済み |
| 6 | 予約の重なり判定 | **半開区間**（終了時刻＝次の開始時刻は重ならない扱い） | そうしないと、連続した枠が全部「重複」と判定される |

### 3番について補足

**税の計算順序は、決めないと必ず5実装で割れる。** 1円のずれが出て、
「どちらが正しいか」を後から議論することになる。

題材の運用ルールにも「金額の計算順序は想定でも1つに決めて明記する」とある。
ここでは **伝票単位・1回だけ・切り捨て** で固定する。

### 4番について補足（裁定を2度変えたので、経緯を残す）

**指揮役は同じ論点で2回裁定を変えた。** 混乱を避けるため、いまの結論と理由を書いておく。

| 目印 | 答える問い | 例 |
| --- | --- | --- |
| **`data-testid`** | **その要素があるか**（存在） | `screen-today` `row-reception` `error-banner` `empty-reception` |
| **`data-check`** | **その値が正しいか**（値） | `billing.net_amount` `progress_note.temperature_c` |

**両方使う。** 片方に寄せない。

経緯:

1. 最初、指揮役は `openapi.yaml` の担当へ「`data-testid` を定義せよ」と指示した
2. 並行して `acceptance.md` の担当が `data-check` を新設した。**衝突に見えた**ので、
   指揮役は「`data-check` に統一。`data-testid` は使わない」と裁定した
3. その後 `openapi.yaml` の設計を実際に読んで、**衝突ではなかった**ことが分かった。
   `data-testid` は要素の存在、`data-check` は値の正しさで、**別の関心**である。
   片方へ寄せると2つを混ぜることになるので、**2番目の裁定を撤回した**

**教訓**: 裁定する前に、両方の設計を読む。**「名前が似ている」は「同じもの」ではない。**
指揮役は名前だけを見て衝突と判断し、実物を読まずに裁定した。

## 2026-09-05 夜 — 契約の欠陥1件を修正（レーンAの指摘 Q-A-08）

**`spec/openapi.yaml` と judge（`tests/checks.py`）が別の項目名を使っていた。**
そのままだと「契約どおり作ったのに落ちる」実装が5つできる。

### どちらが正かを実測で決めた

| 出どころ | 税抜合計 | 未算入件数 | 税込合計 |
| --- | --- | --- | --- |
| `spec/acceptance.md` の `data-check` キー | `net_amount` | `excluded_count` | `total_amount` |
| `tests/checks.py`（judge） | `net_amount` | `excluded_count` | `total_amount` |
| `spec/openapi.yaml` | taxable+nontaxable | excluded_detail_count | total |

**2対1で openapi がずれている。** よって openapi を直した。

### 売上集計は形そのものを変えた

`group_by` で1軸ずつ返す作りだったが、**検算1は3軸を同時に突き合わせる**もので、
この形では成立しない。別々に取ると取った時点がずれる余地も残る。

```
by_category / by_staff / by_date / total_net_amount   ← 同時に返す
```

`from` / `to` は**省略可**にした（judge はパラメータ無しで呼ぶ）。

### 教訓

契約を複数人で分けて書くと、**同じものに別の名前が付く**。
「名前の一覧」を先に決めてから書けば防げた。
`acceptance.md` の `data-check` キー表が実質それになっていたが、
**openapi の担当がそこを見ていなかった。**

## 2026-09-05 夜 — 検算そのものが検算になっていなかった（レーンCの指摘）

レーンC（Laravel）が money を通したとき、こう報告してきた。

> `data/seed.json` の `billing_details[].quantity` は全件整数だったので、
> 「明細ごとに丸めるか合計後に1回で丸めるか」の差は今回のデータでは顕在化しませんでした

**調べたら、そのとおりだった。**

| 調べたこと | 結果 |
| --- | --- |
| 明細600行のうち、数量が非整数のもの | **0行** |
| 伝票150枚のうち、明細ごと丸め ≠ 伝票単位丸め になるもの | **0枚** |
| 単価112件のうち、10で割り切れないもの | 3件（11 / 22 / 33） |

端数の出る単価は**存在するが、1枚の伝票の中で端数が1円以上に積み上がる組み合わせが無い**。

### つまり

**「消費税は伝票単位で1回だけ切り捨て」という規則は、どちらの実装でも緑になる。**
検算2はこの規則について**見張りとして働いていない**。

`PLAN.md` の「緑と呼んでよい条件」に **「見張りを足したら、わざと壊して落ちることを確かめる」**
と書いてあるが、**この検算はそれを通っていなかった**。

### どうしたか

**データを作り直さなかった。** 作り直すと総合計（5,185,704円）が変わり、
既に到達している3実装の検証をやり直すことになる。費用に見合わない。

代わりに**検算そのものを点検する項目を judge に足した**。

```
OK  検算2 この規則を、いまのデータで確かめられているか（検算そのものの点検）
    — ★ 150枚すべてで丸め方の差が出ない。この規則は**いまのデータでは検証できていない**
```

合否ではなく**事実として出す**（常に通す）形にした。赤にすると実装の失敗と紛れるため。

### 教訓

**「検算が緑」と「検算が働いている」は別のこと。**

このプロジェクトは検算9項目を売りにしている。1つでも「何も見ていない」ものが混ざったまま
公開すると、**主張そのものが嘘になる**。

検算を書いたら、**その検算が落ちる入力が実際に存在するか**を確かめること。
存在しないなら、それは検算ではなく飾りである。

## 2026-09-05 夜 — judge 自身にバグがあった（レーンAの指摘 Q-A-10）

**実装ではなく、判定側が間違っていた。**

`tests/checks.py` の `_data_check` は、正規表現で `data-check` 属性を持つ要素を拾っていた。

```python
r"<([a-zA-Z][\w-]*)\b([^>]*?)>(.*?)</\1>"
```

これを `<!DOCTYPE html><html>…</html>` という**普通の文書**に当てると、
拾えるのは **`html` ただ1つ**になる。

`re.finditer` は最も左から始まる一致を返す。`</html>` が文書に1つしか無いので、
`<html>` を起点にした `.*?` が**残り全部を飲み込んで**成立してしまい、
中に入れ子になった `data-check` は一切見つからない。

### 何が起きるところだったか

- **HTMLの書き方の問題ではない。** どの言語・どのスタックで作っても同じように落ちる
- レーンAの実装は**正しく値を出していた**（本人が curl で確認済み）
- screen 組に着手した最初のレーンだったので、**まだ誰の結果にも表面化していなかった**

もし気づかずに進んでいたら、**5実装すべてが「data-check が付いていない」と言われ続け、
5人が自分の実装を疑って直そうとする**ところだった。

### どう直したか

**正規表現をやめ、`html.parser` で書き直した。** 入れ子も正しく扱う。

```
普通の文書   → ['1', '2']      （以前は []）
入れ子あり   → ['3,500']       （<b>3</b>,500 を1つの値として読む）
属性が後ろ   → ['7']
目印なし     → []
```

直後にレーンAの実装で測り直したら、**screen 3件が緑になった**。実装は最初から正しかった。

### 教訓

**判定する側が間違っていると、正しい実装が落ちる。** しかも落ちた側は
自分を疑うので、間違いが見つかるまで時間が溶ける。

`PLAN.md` に「見張りを足したら、わざと壊して落ちることを確かめる」と書いたが、
**「見張りが正しいものを通すか」も確かめる必要がある**。落ちることだけ確かめても足りない。

レーンAは「止まらず進めるべき点は無いか検討したが、tests 側の修正を待つほかない」と
判断して報告してきた。**これは正しい。** `PROTOCOL.md` の「止まらない質問は仮決めして進む」は、
**仮決めで進める場合の話**であり、判定側が壊れているときは進めない。

## 2026-09-06 — judge のバグ2件目（レーンDの指摘）

**HTTPのヘッダ名は大文字小文字を区別しない**（RFC 9110）のに、judge は区別して読んでいた。

```python
headers.get("Content-Type", "")   # ← これ
```

実測すると、実装によって返し方が違う。

| 実装 | 返すキー |
| --- | --- |
| Go | `Content-Type` |
| Laravel | `Content-Type` |
| **FastAPI / Starlette** | **`content-type`** |

FastAPI では `get("Content-Type")` が常に `None` になり、
`_dead_links` の「HTMLでなければ辿らない」判定が**全ページで真**になって、
**トップの1画面しか辿れなかった**。

### 何が起きるところだったか

レーンAは Go で、Go は慣習的に `Content-Type` を返す。**だから表面化しなかった。**
FastAPI のレーンDが最初に当たった。

もし気づかずに進んでいたら、**FastAPI と Next.js だけが検算8を通せない**という
「実装の質の差」に見える現象が残るところだった。**実際は判定側の欠陥**である。

### どう直したか

`Client` の側でヘッダのキーを**小文字へ正規化**した。判定する側が
**実装の書き癖に左右されてはいけない**ので、入口で揃える。

直後の実測: FastAPI が **60画面**を辿って切れなし（以前は1画面）。Go は回帰なし。

### 教訓

**judge のバグは、実装の差として現れる。**

今回も前回（`_data_check` の正規表現）も、**特定のスタックだけが落ちる**形で出た。
「あの実装だけ通らない」を見たら、**まず判定側を疑う**こと。

そして今回も、レーンDは「まず自分の側を確かめてから」の順序を守り、
curl でリンクが出ていること・`Client.get` のヘッダが小文字であることを
**実測してから**報告してきた。

## 2026-09-06 — judge の欠陥3件目（レーンCの発見から）

レーンCは検算8で「1画面しか辿れない」に当たり、**自分のミスとして**報告してきた。

> 共通レイアウトのナビ等を `url('/xxx')` で書いていた。Laravelの `url()` は絶対URL
> （`http://127.0.0.1:8403/xxx`）を返すため、共通クローラーの `href="/..."` 判定に
> 掛からず、リンクとして1つも拾われていなかった

**が、これは判定側の問題でもある。**

絶対URLは正しいHTMLであり、ブラウザは普通に辿る。拾えないままだと、
**判定側が実装に「ルート相対で書け」と強制する**ことになる。

`spec/README.md` は「**画面の見た目は各スタックの流儀でよい。揃えるのは振る舞いだけ**」と
定めている。**書き方の強制はこれに反する。**

### どう直したか

巡回器が**絶対URLも辿る**ようにした。ただし**同じ相手のものだけ**で、外のサイトへは出ない。

直後の実測: Go 14画面 / Laravel 60画面 / FastAPI 60画面。回帰なし。

### 途中で自分が壊した

定義（`HREF_RE`）を入れ忘れたまま使用箇所だけ差し替え、3実装とも
`NameError` で落とした。**judge が「検査自体が落ちた」と報告した**ので、
すぐ原因が分かった。検査の中で例外を握って合否に混ぜず、
**壊れたことを壊れたと出す**作りにしておいてよかった。

### 判定側の欠陥はこれで3件目

| # | 何が | どう現れたか |
| --- | --- | --- |
| 1 | 正規表現が普通のHTML文書を読めない | 全実装で `data-check` が0件 |
| 2 | HTTPヘッダを大文字小文字で区別 | **FastAPI だけ**1画面しか辿れない |
| 3 | 絶対URLを辿らない | **Laravel だけ**1画面しか辿れない |

**3件とも「特定の実装だけが落ちる」形で出た。** 実装の質の差に見えるが、
中身は判定側の欠陥である。

**「あの実装だけ通らない」を見たら、まず判定側を疑うこと。**
