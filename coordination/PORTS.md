## なぜ決めるのか

2026-09-05 の実測では A=8412 / B=3002 / C=8003 / D=8004 / E=3005 とバラバラで、
**たまたま重ならなかっただけ**だった（レーンRの指摘 R-03）。

Rails と Next.js は既定がそれぞれ 3000 番台で、**何もしなければ衝突する**。
5つ同時に立ち上げる前提なので、決めておかないと再起動のたびに事故る。

8401〜8405 に揃えたのは、**番号を見ればレーンが分かる**ようにするため
（末尾の1〜5がA〜Eに対応）。

## レーンD のポートが2度変わった理由（2026-09-05〜06）

**8404 は、プロセスが存在しないのに LISTEN が残る状態になった。**

`Get-NetTCPConnection` は所有PID 22928 を示すが、`Get-Process` にも `tasklist` にも
そのPIDは無い。`Stop-Process` も `taskkill` も「そんなプロセスは無い」と言う。
それでも `curl` は応答を返す。Windowsで稀に起きる、**握ったまま死んだソケット**である。

指揮役が起動した FastAPI のサーバを2つ止めたが、それでも解放されなかった。

機械の都合で作業が止まるのは無駄なので、レーンD を 8414 へ移した。

**その 8414 でも同じことが起きた**（2026-09-06）。今度は指揮役が
`Stop-Process -Force` で止めた直後に再現している。

レーンDの見立て: **強制終了がソケットの後始末を妨げている。**
uvicorn がソケットを正常に閉じる前にプロセスを殺すと、
Windows 側にリスニングの記録が残るのではないか。

そこで **8415** へ移し、あわせて**強制終了を使わない**ことにした。
止めるときは Ctrl+C 相当（`SIGINT`）で、後始末を待つ。

8404 と 8414 は再起動すれば戻る見込み。
