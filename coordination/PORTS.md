## レーンD のポートが2度変わった理由（2026-09-05〜06）

**8404 は、プロセスが存在しないのに LISTEN が残る状態になった。**

`Get-NetTCPConnection` は所有PID 22928 を示すが、`Get-Process` にも `tasklist` にも
そのPIDは無い。`Stop-Process` も `taskkill` も「そんなプロセスは無い」と言う。
それでも `curl` は応答を返す。Windowsで稀に起きる、**握ったまま死んだソケット**である。

指揮役が起動した FastAPI のサーバを2つ止めたが、それでも解放されなかった。

機械の都合で作業が止まるのは無駄なので、レーンD を 8414 へ移した。

**その 8414 でも同じことが起きた**（2026-09-06）。今度は指揮役が
`Stop-Process -Force` で止めた直後に再現している。

### 正体は「死んだソケット」ではなく**孤児プロセス**だった（2026-09-06 訂正）

レーンDが追い直して原因を突き止めた。**私（指揮役）の当初の見立ては誤りだった。**

`Stop-Process` で止めていたのは WatchFiles の reloader（親）だけで、
**multiprocessing で fork した worker（子）が生き残ってソケットを掴み続けていた**。

`Get-NetTCPConnection` が示すPIDが `Get-Process` で引けなかったのは、
**そのPIDが既に死んだ親のものだったから**で、実際に掴んでいたのは別の子である。

見つけ方:

```powershell
Get-CimInstance Win32_Process |
  Where-Object { $_.CommandLine -like '*multiprocessing.spawn*' }
```

親が存在しない子を洗い出して個別に止めたところ、**8404 も 8414 も解放された**。

**対処**: reloader を止めるときは**子プロセスも一緒に止める**。
「プロセスが無いのにポートが埋まっている」と見えたら、**孤児を疑う**。
