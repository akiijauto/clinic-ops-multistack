# 計画 — 同じ業務システムを5つの技術スタックで同時に作る

作成 2026-09-05。**この文書が計画の正本。** 矛盾を見つけたらこれに従い、指揮役へ報告する。

## ゴール

> **指揮役がオーナーへ質問することなく、実装からテスト・公開ゲート通過まで完走する。**

「聞かずに済ませる」ためには、**聞く必要が出る事柄を計画の段階で全部潰しておく**必要がある。
本文書と `DECISIONS.md` はそのために書かれている。

**例外は1つだけ。** リポジトリを public に切り替える操作は、CLAUDE.md により
オーナーの明示的な承認が必須である。これは省略できないし、省略しようとしてはいけない。
**完走の定義は「private リポジトリに、テストが通り、公開ゲートを通過した状態で置かれていること」**とする。

## 何を作るか

動物病院の窓口業務システム **全24画面**を、**5つの技術スタックで各1実装**。

同じ仕様・同じ受け入れテストに対して5つが独立に通ることを確かめる。
狙いは機能の多さではなく、**「同じ問題を別の道具で解くと何が変わるか」を実測して言語化すること**。

### 対象は「これから出来上がる姿」である（重要）

**題材にしている業務システムは、いま作りかけの部分を埋めている最中である。**
2026-09-05 の実装計画で、画面に残っていた**灰色のボタン41個のうち38個を動かす**ことが決まった。
そこには**新しい画面が2つ**含まれる（予約・売上集計）。

つまり **対象が動いている。** ここを踏まえないと、契約を凍結した先から古くなる。

**対処**: 契約は**現在の姿ではなく、計画で決まっている姿**に対して書く。
実装計画は担当・画面・振る舞いまで具体的に書かれているので、そこから仕様を起こせる。
出来上がるのを待つ必要はない。

**やってはいけないこと**: 出来上がるまで待って、それから写す。
待てば本計画の並列は成立するが、**題材が動くたびに止まる**ことになる。

### 画面の内訳（5領域・26画面）

**この分け方が、そのままレーン内のサブエージェントの分担になる。**

| 領域 | 画面 |
| --- | --- |
| **1 受付・患者** | 一覧 / 新規 / 顧客 / 検索 / 来院履歴 / 削除 / 折りたたみ表示 / トップ |
| **2 診療** | カルテ / 検査 / 投薬 / 予防 / 書類 |
| **3 会計・売上** | 会計 / 会計履歴 / DM / **売上集計（新）** |
| **4 入院・予約・業務** | 入院 / **予約（新）** / ToDo / スタッフ |
| **5 設定** | 設定 / 機能設定 / 取込 / マスタ / このシステムについて |

（既存24画面 ＋ 新規2画面）

### 規模（実測）

| | 値 |
| --- | ---: |
| 既存システムの画面テンプレート | 24枚 |
| これから足される画面 | 2枚（予約・売上集計） |
| これから動くようになるボタン | **38個**（41個のうち3個は「作らない」と決めたもの） |
| 既存システムの `app/` の Python | 15,700行 |
| 1スタックあたりの想定（テスト込み） | **26,000〜33,000行** |
| 参考：RetailBrain（2026-09-04、3レーン、7.3時間） | 7,896行 |

**RetailBrain の約4倍**である。

灰色のボタン38個は「見た目を足す」話ではなく、**その裏の処理を作る**話である。
絞り込み・上下送り・診察券の発行・番号の変更・CSVの書き出し・ログイン——
どれも画面1枚ぶんの実装に相当するものが混ざっている。
**画面数は26だが、作る量は26画面ぶんでは済まない。**

### スタック（5レーン）

**すべて追加インストール不要**であることを 2026-09-05 に実測して選んだ。
新しい実行環境の導入はオーナーの確認が要る（CLAUDE.md）ので、そこで止まらないようにするため。

| レーン | バックエンド | 画面 | 導入済みバージョン |
| --- | --- | --- | --- |
| **A** | Go（`net/http` のみ） | `html/template` | Go 1.27.0 |
| **B** | Ruby on Rails | Hotwire / ERB | Rails 8.1.3.1 |
| **C** | PHP / Laravel | Blade | PHP 8.4.24 / Composer 2.10.3 |
| **D** | Python / FastAPI | Jinja2 | Python 3.14.3 |
| **E** | TypeScript / Next.js | React | Node 24.16.0 |

各レーンは**そのスタックの流儀で書く**。無理に揃えない。
揃えるのは**外から見た振る舞い**だけで、それは下記の契約が定義する。

## 並列の構造（2階建て）

24画面を1つのレーンが抱えるのは無理がある。かといってレーンを25本
（5スタック × 5領域）に増やすと、**指揮役が窓口を25個持つことになり、そこが詰まる**。

そこで**2階建て**にする。

```
指揮役（1）
  │  窓口は5つだけ
  ├── レーンA (Go)      ── 内部でサブエージェント（領域1〜5）
  ├── レーンB (Rails)   ── 内部でサブエージェント（領域1〜5）
  ├── レーンC (Laravel) ── 内部でサブエージェント（領域1〜5）
  ├── レーンD (FastAPI) ── 内部でサブエージェント（領域1〜5）
  └── レーンE (Next.js) ── 内部でサブエージェント（領域1〜5）
```

- **指揮役が話す相手は5レーンだけ。** RetailBrain で実証済みの規模を超えない
- **各レーンは自分の中で領域ごとにサブエージェントを走らせる。** 実際の並列度は20〜25
- サブエージェントの管理は**各レーンの責任**であり、指揮役は関与しない

### 書かずに読むだけの役を1つ置く（レーンR）

**実装しないレーンを1つ用意する。** 題材の実装計画（2026-09-05）から採った仕組みで、
そこにはこう書かれている。

> 2026-09-04 の RetailBrain では、見つかった間違い12件のうち**6件はこの見方でしか出なかった**

**指揮役が5レーンの中身を全部読むのは無理**なので、この役がその穴を埋める。
書き換えず、次の3つだけを見る。

1. **画面に嘘が無いか。** 「できます」と書いてあって出来ていないもの
2. **緑のまま壊れていないか。** テストをわざと壊して、ちゃんと落ちることを確かめる
3. **仮決めが仮決めと分からない形で紛れていないか**

3つ目は特に効く。**この計画は「止まらない質問は仮決めして進む」ことにしている**（`PROTOCOL.md`）ので、
仮決めが記録されないまま実装に溶けると、後から誰も気づけない。

レーンRは `coordination/review/` に見つけたものを書く。**直さない。** 直すのは担当のレーン。

この形は 2026-09-05 に実証済みである。同日のPHP実装では、1つのセッションが
4つのサブエージェント（HTTP層・DB層・生成層・インフラ）を並列に走らせ、
**統合点だけを自分で書いた**。同日のサーバーレス移行も3サブエージェントで同じ形をとった。

**レーン内でも、統合点（各領域をつなぐ部分）はレーン本体が自分で書くこと。**
サブエージェント同士に統合させると、境界の認識がずれて後で合わなくなる。

### 機械の制約（実測）

| | 値 |
| --- | ---: |
| CPU | 8物理コア / 16論理 |
| メモリ | 31.3GB（うち空き 14.0GB） |
| CLI 1つあたりの実測メモリ | 150〜500MB |

**5つのCLIなら余裕がある。** サブエージェントは各CLIの中で動くので、
プロセス数は増えても管理の窓口は増えない。

## 成立条件（これが無いと破綻する）

> **5レーンすべてを、同じテストで判定できること。**

これが無いと「動くように見えるが誰も検証していないもの」が5つできる。
実際、2026-09-05 のPHP実装では**ライブラリの鍵長制約・言語の既定引数の意味論・
`json_encode` の正規化**の3件が、走らせて初めて見つかった。
書けることと正しいことは別である。

そこで、**言語に依存しない judge をひとつ作る**。

- `spec/openapi.yaml` — HTTPの契約。ここが唯一の正
- `tests/` — **HTTP越しに叩く受け入れテスト**。実装言語を問わない
- `spec/acceptance.md` — 画面と数値の受け入れ条件（検算を含む）

各レーンは「自分のテストが通った」ではなく、**「共通の judge が通った」**で完了とする。

## 進め方

### 第0段階：契約の凍結（直列・指揮役のみ）

**ここだけは並列にしない。** 全レーンがこれを前提に動くので、途中で変わると全部やり直しになる。

1. `spec/openapi.yaml` を書く（エンドポイント・要求・応答・エラー）
2. `spec/acceptance.md` を書く（画面の受け入れ条件・検算のルール）
3. `tests/` に共通テストを書き、**参照実装なしで動くことを確認する**（全部赤で始まる）
4. `data/` に合成データを置く（全レーンが同じ入力を使う）
5. **凍結を宣言する。** 以後の変更は全レーンを止めて指揮役が判断する

見積もり **8〜11時間**（26画面ぶん、および動くようになる38個の振る舞いを書くため）。

### 第1段階：全レーン起動と疎通確認（並列）

各レーンを起動し、**最初のマイルストーンだけを見る**。

> **全レーンが自分の担当を正しく認識し、共通テストの1件目が通ること。**

RetailBrain（2026-09-04）で、3つのCLIに**同一の起動文面**を貼ったために各CLIが自分のレーンを
知らずに起動し、割当が二転三転する事故が起きた（`retailbrain/coordination/ASSIGNMENT.md` に記録）。
**レーンが増えるほど確実に悪化する**ので、ここで壊れるなら早く分かったほうがいい。

対策は単純で、**レーンごとに違う起動文面を貼る**。`briefs/lane-*.md` がそれで、
1文目に必ずレーン名が入っている。

見積もり **30分**。ここが通らなければ先へ進まない。

### 第2段階：実装（並列）

各レーンが共通テストを緑にする。レーン間の依存は無い（契約は `spec/` だけ）。
**各レーンは内部でサブエージェントを領域ごとに走らせる。**

見積もり **28〜38時間**。RetailBrain の実績（7,896行 / 7.3時間 = 約1,080行/時）を
1スタック 26,000〜33,000行へ当てはめた値。レーン内のサブエージェント並列が効くので、
1レーンあたりの実時間はこの範囲に収まる想定。

**ただしこの換算は楽観に振れている可能性がある。** RetailBrain は白紙から作った
新規開発で、契約さえ守れば中身は自由だった。今回は**既に決まっている振る舞いに
合わせる**ぶん、行あたりの手間が増える。2026-09-05 のPHP移植は 約400行/時 だった
（既存3実装と一字一句合わせる必要があったため）。実際は両者の間に落ちる見込み。

### 第3段階：突き合わせ（直列・指揮役）

5実装の**振る舞いの差**を洗う。ここを小さく見積もらない。
2026-09-05 の実測では、移植で踏んだ不具合は**すべてこの段階で出た**。

- 同じ入力に同じ応答を返すか（テストが通っていても、テストに無い入力でずれる）
- エラーの文言・ステータスコードが揃っているか
- 数値の丸め・タイムゾーン・文字数の数え方

**画面が26枚あり、動く機能も増えたので、ここは相応に重くなる。**

見積もり **14〜18時間**。

### 第4段階：公開準備（直列・指揮役）

READMEに**学習目的**と**複製禁止**を明記し、公開ゲートを通す。
**public への切り替えはここではやらない**（オーナーの承認事項）。

見積もり **4〜5時間**。

### 合計

| 段階 | 実時間 | 並列 |
| --- | ---: | --- |
| 第0段階 契約の凍結 | 8〜11時間 | 直列 |
| 第1段階 疎通確認 | 0.5時間 | 並列 |
| 第2段階 実装 | **28〜70時間**（下記） | **並列（5レーン × 各4〜5サブ ＋ レーンR）** |
| 第3段階 突き合わせ | 14〜18時間 | 直列 |
| 第4段階 公開準備 | 4〜5時間 | 直列 |
| **合計** | **55〜105時間 ≒ 実働7〜13日** | |

**幅が広いのは、行あたりの手間が読めないため。** 上限は「既に決まっている振る舞いに
合わせる」PHP移植の実績（400行/時）で置いた。下限は白紙からの新規開発（1,080行/時）。
**実測が取れたら置き換える**（レーンRの指摘 R-13）。

**改訂前は 40〜55時間（5〜7日）としていた。** 題材が「灰色のボタンを全部なくす」
実装に入り、画面が2枚増え、38個の機能が動くようになるぶんを織り込んで上げた。

**並列で縮むのは第2段階だけ**である。RetailBrain の実測では、3レーン並列が全体に効いたのは
**21%の短縮**だった（441分のうち、並列区間59分が直列なら177分相当）。

したがって **「速くするために並列にする」のは費用対効果が悪い。**
並列の価値は**同じ時間で桁違いの量を出すこと**にある。

**5スタックを1つずつ順に作れば、実装だけで 140〜190時間（実働18〜24日）。**
それを 55〜73時間（実働7〜9日）で出すのがこの計画である。

## 何を主張できるようになるか

- **同じ仕様を5つのスタックで実装し、同じテストで検証した**
- 実装ごとの差（実行イメージの大きさ・起動時間・行数・何を自分で書くことになるか）を**実測値で**語れる
- **AIエージェントを2階建てで並列に使い、順に作れば実働18〜24日の量を7〜9日で出した**という工数の比較
  （5スタック × 26,000〜33,000行。1スタックずつ順に作った場合との比較）

最後の点について。**「通常なら〇日」の根拠を作り話にしない。**
比較は**自分の実測どうし**で行う。すでに手元にある数字はこれ:

| 実測 | 値 |
| --- | --- |
| 同じAPIを2つ目の言語（Go）で書く | Week5 実績 |
| 3つ目（PHP、4エージェント並列） | 約6時間 / 約2,400行 |
| インフラだけ替える（サーバーレス移行、3エージェント並列） | 約2時間 |
| 3レーン並列で新規開発（RetailBrain） | 7,896行 / 7.3時間 |

**言えるのはここまで。** 「通常の開発者なら何日」は手元に実測が無いので書かない。
比較の軸は「**自分が順に作った場合**」対「**並列で作った場合**」に限る。

## 緑と呼んでよい条件

題材のリポジトリで積み上がった作法をそのまま通す。**これを緩めると、
5実装ぶんの「通ったつもり」が積み上がる。**

1. **最後のコミットのあとに全体を流す。** 部分実行の緑を緑と呼ばない
2. **見張りを足したら、わざと壊して落ちることを確かめる。** 落ちないテストは無いのと同じ
3. **死んだリンクが無いこと**を機械で確かめる（画面が26枚あるので目視は無理）
4. **画面が崩れないこと**を複数の幅で確かめる
5. 指揮役は**自己申告ではなく自分で共通テストを走らせて**判定する

## 中止条件

次のいずれかに当たったら、**進めずに指揮役が止めてオーナーへ報告する**。

1. 第1段階で、レーンの担当認識がどうしても揃わない
2. 契約（`spec/`）を変えないと実装できないレーンが**2つ以上**出た
   （1つなら、そのレーンの読み違いを疑う。2つ以上なら契約の欠陥）
3. 新しい実行環境のインストールが必要になった（CLAUDE.md により確認事項）
4. 合成データに、実在の個人・法人を特定できる情報が混ざった疑いが出た
