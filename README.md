# clinic-ops-multistack

**同じ仕様を Go / Ruby on Rails / PHP Laravel / Python FastAPI / TypeScript Next.js で実装し、
言語を問わない判定器30項目で、5実装が同じ答えを出すことを確かめた記録です。**

**判定器自身の欠陥が10件出ました。うち8件は、判定器を書いた本人（まとめ役）が作ったものです。**
その経緯も全部残してあります。

| **5実装を見比べる** | https://ai-l-a-b-o.com/clinic-ops-compare/ （本物のブラウザで撮った画面を横並び） |
| **失敗の記録** | [`coordination/review/2026-09-06_指揮役の反省.md`](coordination/review/2026-09-06_%E6%8C%87%E6%8F%AE%E5%BD%B9%E3%81%AE%E5%8F%8D%E7%9C%81.md) |

## 実測（2026-09-06）

| 確かめていること | 結果 |
| --- | --- |
| 共通テスト | 5実装 × **30項目すべて通過**、食い違い0 |
| 契約のルート | 画面42 / API36 — **確かめられないもの0件** |
| 税抜売上の総合計 | 5実装とも **5,189,585円**（判定器が `data/` から独立に計算した値と一致） |
| 消費税の丸め規則 | 150枚中132枚が丸め方を区別する（**検算が実際に働いている**） |

期待値は `tests/expected.py` が **`data/` から独立に計算**します。**実装のコードを一切通しません。**
実装が返した数字を実装の理屈で検算しても、同じ間違いを2回するだけだからです。

## 出来ていないこと

- **カルテと検査は、実装ごとに画面の情報量が違います**（表の数が0〜7）。
  売上集計は FastAPI だけ「日別」の表がありません。**数字は一致しますが、画面に出る量は揃っていません**
- 公開版は**読み取り専用**です（保存・削除は403で断ります）
- 実運用していません。**データはすべて架空**で、実在の動物病院・飼主・動物の情報は含みません

## この記録でいちばん価値があると考えているもの

**実装ではなく、判定器と、その失敗の記録です。**

- **緑は「壊れていない」の証明であって、「出来ている」の証明ではない**
- **赤も「出来ていない」の証明ではない。** 判定器が間違っていれば、正しい実装ほど落ちる
- **多数決を根拠にするな。** 5つのうち4つが通っていることは、その4つが正しい証明ではない

まとめ役の判断ミスが5件あり、**5件とも本人以外が指摘して分かりました。**
`coordination/` にその往復がそのまま残っています。

## 何を確かめているか

機能の数ではなく、**「5つの実装が同じであることを、どう保証するか」**です。

### 判定は1つだけ

`tests/run.py` が唯一の物差しです。**実装の言語を問わず、HTTP越しに叩くだけ**なので、
Go でも Rails でも Laravel でも FastAPI でも Next.js でも同じ問いを投げます。

期待値は `tests/expected.py` が **`data/` から独立に計算**します。
**実装のコードを一切通しません。** 実装が返した数字を実装の理屈で検算しても、
同じ間違いを2回するだけだからです。

### 実測（2026-09-06 時点、`tests/compare.py` を実行して確認）

**5実装すべてが、共通テスト22件を全部通過。食い違いは0件です。**
（2026-09-05時点は14件でしたが、その後「在庫検査」など8件を足しています。）

| 検査 | Go | Rails | Laravel | FastAPI | Next.js |
| --- | :-: | :-: | :-: | :-: | :-: |
| `/healthz` が `{"status":"ok"}` を返す | OK | OK | OK | OK | OK |
| 売上が分類別・担当別・日別・総合計で一致 | OK | OK | OK | OK | OK |
| 分類別の構成比の和がちょうど 100.0% | OK | OK | OK | OK | OK |
| 単価未設定の行を0円で合計に入れない | OK | OK | OK | OK | OK |
| 消費税は伝票単位で1回だけ切り捨て | OK | OK | OK | OK | OK |
| 体温・カルテ印刷一致・予約重複なし・入院実施者・削除の扱い（検算3・4・6・7・9） | OK | OK | OK | OK | OK |
| 画面のリンクが全部生きている（検算8） | OK | OK | OK | OK | OK |
| 契約の画面・APIルートが実装に在る（在庫検査、後述） | OK | OK | OK | OK | OK |

`tests/expected.py` が `data/` から独立に計算した期待値と一致しています。

## 途中で見つかったもの

**「通っている」と「確かめられている」は別のことだ**という例が、
2026-09-05時点で3つ、2026-09-06にさらに3つ出ました。
最初の3つは実装した本人ではなく**別の役割から見つかっています**。
4つ目はオーナーの指摘で、5つ目は統括役自身が気づいて記録したものです。

### 1. smoke が緑でも健全とは限らない

Next.js 版で、**DBに触るAPIルートが全部 500** を返していました。
原因は `import.meta.dirname` がバンドル後に `undefined` になることで、
`node --test` では通るため気づけません。

> smoke は `/healthz` しか叩かないので、これまで気づかれていなかった

**緑の範囲が狭いと、その外側は見えません。**

### 2. 検算が緑でも、働いているとは限らない

「消費税は伝票単位で1回だけ切り捨て」という規則が、**150枚すべての伝票で
どちらの実装でも緑になる**状態でした。明細の数量が全件整数だったためです。

つまりこの検算は、**何も見張っていませんでした**。
いまは judge に「この検算は働いているか」を点検する項目を足し、
**事実がテスト結果に出る**ようにしてあります。

### 3. 契約を分けて書くと、同じものに別の名前が付く

`spec/openapi.yaml` と判定側で、金額の項目名が食い違っていました
（`taxable_subtotal` / `net_amount`、`excluded_detail_count` / `excluded_count`）。

**5実装のうち4つが、独立にこれを報告してきました。** 全員が待たずに仮決めして進み、
記録を残しています。待っていたら5つとも止まっていました。

### 4. 「テストが緑」を「完了」と読んだ（2026-09-06、オーナーの指摘で発覚）

共通テスト14件が5実装とも緑・食い違い0になったのを見て、**統括役がそれをもって
「完了」と判断**し、公開ゲートを通してコミット・pushした。実際にはレーンの報告に
「未完了。残り23画面・26 API」とはっきり書いてあった。**読まずに緑だけで判断した。**

> **緑は「壊れていない」の証明であって、「出来ている」の証明ではない。**
> 出来ているかは、作るものを数えて、数えたものが在ることを確かめないと分からない。

対策として、契約（`spec/openapi.yaml`）のルートを1件ずつ直に叩いて在庫を数える
`tests/inventory.py` を足した（前節の在庫検査はこれの結果）。

### 5. 判定器の欠陥がここまでで6件。うち少なくとも3件は統括役自身が作ったと明記されている

判定器（`tests/`）の欠陥はこれまでに6件記録されている。最初の3件（正規表現がHTML文書を
読めない・HTTPヘッダの大文字小文字・絶対URLを辿らない）は各レーンが自分の実装を疑って
から見つけたもので、`coordination/qa/rulings.md` に「誰が作ったか」の記載は無い
（**未確認**）。後の3件は、統括役が在庫検査（`tests/inventory.py`）を書く過程で
自分で作ったと本人が明記している——実データを見ずにパス変数を直に書いて
「実装があるのに404」と報告した、500番エラーを「在る」の側に数えていた、
目印（`data-testid`）を確かめる検査自体が無かった。

**赤も「出来ていない」の証明ではない**——判定器が間違っていれば、契約を守った
実装ほど落ちる。「5つのうち4つが通っている」を根拠に残る1つへ「直せ」と指示した
場面が2件あったが、どちらも判定器の側が誤っていた（後述の予約API調査でも、
このパターンが繰り返し起きている）。

詳しくは `coordination/review/2026-09-06_指揮役の反省.md` と `coordination/qa/rulings.md`。

## どこまで作ってあるか（実測・2026-09-06 11:50 時点）

**2026-09-05時点の本節は「26画面を作り切ってはいない」「共通テスト14件が通る範囲」
と書いていた。その時点では正しかった。** その後、5レーンが並列で残りの画面・APIを
配線し、以下まで進んだ。**ただし「すべて実装済み」と言い切るのは早い**——
下の「読む側で見つかった穴」節にある通り、GETでは見えない欠陥が実際に残っている。

- 契約（`spec/openapi.yaml`）が定義する**画面ルート42件・APIルート36件（計78件）
  のうち75件**を、5実装すべてで直接GETして確認できた（`tests/inventory.py`）
- 残り3件（画面2件＋API1件、いずれも書類=紙カルテPDFの個別参照・削除）は
  **「無い」でも「在る」でもなく「確かめられない」**。`data/seed.json` に該当データが
  無いため自動検査は判定を保留する。**手で個別に叩くと、どのIDが存在するかは
  サーバーの起動来歴（誰がいつテスト用に1件作ったか）に左右され、時刻によって
  結果が変わる**——実際、11:41の実測ではRailsのみ`/papers/1`が200、
  11:49に本レーンが取り直したときはRailsとFastAPIが200・残り3実装は404だった。
  **同じ問いに、測るたびに違う答えが出る状態**であり、「40/42・35/36が在る」という
  数え方に足すのは誤り
- 共通テストは22件に増え、5実装とも全通過（食い違い0）——ただし、この22件は
  **GETしか送らない**（下記参照）

### 読む側（監査）で見つかった穴——GETでは見えない書き込み経路の欠陥

共通テスト（`tests/checks.py` の検算6を含む）と在庫検査（`tests/inventory.py`）は、
**ソースを確認する限り、POST/PUT/DELETEを一度も送らない。** 予約の重なり判定（検算6）も、
既に`data/seed.json`からDBへ投入済みの60件をGETで読むだけで、実際に予約を
新規作成する経路は検査していない。

このレーンで `POST /api/reservations` を5実装へ実際に送って確かめた
（2026-09-06 11:49、契約どおり `starts_at` にタイムゾーン付き日時
`2099-03-15T09:00:00+09:00` を渡した）。

| 実装 | 結果 |
| --- | --- |
| Go | `201` 正常に作成 |
| Rails | `201` 正常に作成 |
| Laravel | `201` 正常に作成 |
| **FastAPI** | **`500 Internal Server Error`** |
| Next.js | `201` 正常に作成 |

同じ内容でオフセット無し（`2099-03-16T09:00:00`）にすると FastAPI も `201` で通る。
**`data/seed.json` の予約データは全件がオフセット付き形式**なので、契約どおりに
タイムゾーンを付けて送るクライアントほどこのバグを踏む。この欠陥は
`coordination/review/2026-09-06_4巡目.md`（レーンR、07:30）で先に報告されており、
**指揮役への報告後もFastAPI側は直っていない**（本レーンで再現、11:49時点）。
なお同じ調査でRails・Laravelにも別の欠陥（JSON APIのcreate/update/cancelが
404・405を返す）があると07:30時点で報告されていたが、11:49時点の再測では
両方とも直っており201が返っている。

> 共通テストが22件全通過・食い違い0なのは事実だが、**その外側に、
> 実際に壊れているエンドポイントが現存する。** 検査がGETしか送らない限り、
> 書き込み系の欠陥は原理的に見えない。

詳しくは `coordination/review/audit-指揮役.md`（レーンS、指揮役の主張5件のうち
2件を「根拠が届いていない」と判定）と `coordination/review/2026-09-06_4巡目.md`。

### まだ確かめられていないこと（上記以外）

- 消費税の丸め規則（伝票単位で1回だけ切り捨て）は、**150枚すべての伝票で丸め方の
  差が出ないため、いまのデータでは検証できていない。** 検算は緑だが、その緑は
  「規則が正しく実装されている」ことの証明ではない
- 契約に「PDF以外の形式のファイルは取り込みを拒否する」とあるが、5実装のいずれも
  ファイルアップロードの実体（`multipart/form-data`）を持たず、取込は記録
  （メタデータ）のみを扱っている。**この条件は未検証**（裁定R-21、`spec/screens.md`）
- 見た目の一致は「共通CSSを配布し、契約が求める3クラスがどこかの画面に現れる」ことの
  確認どまりで、**画面ごとに実際に同じ見た目でレンダリングされているかは検査していない**
  （目視・スクリーンショット比較は未実施）

5実装の行数は 7,100〜12,100行（自分で書いたぶん、依存の実体を除く。2026-09-05時点は
2,300〜4,700行だった）。計画では1実装 20,000〜25,000行と見込んでいた。
詳しくは `coordination/実績-2026-09-06.md` に書いた（数え方・前回との比較つき）。

**「画面に できます と書いて出来ていない状態を作らない」**（`spec/README.md`）ため、
保存・登録・編集のフォームを繋いでいない画面には、押せる保存ボタンを置いていない。

## 構成

```
spec/           契約。ここが唯一の正
  README.md       範囲・振る舞いの原則・HTMLの目印
  model.md        データの形（14モデル）と、落としたものの理由
  screens.md      26画面それぞれの「満たすべきこと」
  acceptance.md   検算9項目
  openapi.yaml    HTTPの契約
tests/
  run.py          判定。実装の言語を問わずHTTPで叩く
  expected.py     期待値を data/ から独立に計算する
  checks.py       検算9項目の実体
  compare.py      5実装を横並びに測り、食い違う行だけを出す
data/           合成データ。生成スクリプトつき（乱数の種は固定）
stacks/
  go/  rails/  laravel/  fastapi/  nextjs/
coordination/   並列開発の進め方（計画・割当・ルール・裁定の記録）
```

## 動かし方

各実装のポートは `coordination/PORTS.md` にあります。

```bash
python tests/run.py http://127.0.0.1:8401          # 1つを測る
python tests/run.py http://127.0.0.1:8401 --only money
python tests/compare.py                            # 動いているものを全部並べる
python tests/expected.py                           # 期待値だけを見る
```

判定は依存を足していません（Python の標準ライブラリだけ）。
5つの環境で同じものを走らせるので、入れるものが増えるほど「動かない理由」が増えるためです。

## 進め方の記録

`coordination/` に、**5つのCLIを並列に走らせて1人が統括する**やり方の記録があります。

- `PLAN.md` — 計画と見積もり（実測で更新している）
- `PROTOCOL.md` — 守るルール。**止まらない質問は仮決めして進む**など
- `DECISIONS.md` — 実装中に判断で止まらないよう、先に決めてあること
- `qa/rulings.md` — 統括が下した裁定と、**その理由**
- `review/` — 書かずに読むだけの役が見つけたもの
